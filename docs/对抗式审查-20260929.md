# 对抗式审查：各功能是否合理且有效

日期：2026-09-29　方法：全部结论用 `data/zkai.db` 的 35,548 条请求 / 64,000+ 次尝试
实证，不用印象。凡"我认为"处都标注了证据强度。

---

## 0. 一句话结论

**我这几轮加的五个机制里，只有一个是数据支持有效的；最大的浪费（63 小时等待、
8 亿输入 token）与我的改动无关，且我修过的东西都没解决它。**

---

## 1. 最大浪费：不是路由，是"等死掉的部署"

按部署统计累计墙钟（`request_attempts.latency_ms` 求和）：

| 部署 | 尝试 | 成功 | 成功率 | 累计耗时 |
|---|---|---|---|---|
| step-5-preview-StepFun | 27,802 | 27,747 | **99.8%** | 66.5h（有效工作） |
| kimi-k3-sensenova | 13,419 | 4,421 | 32.9% | 28.0h |
| **kimi-k3-nvidia** | 2,967 | 33 | **1.1%** | **32.6h** |
| **glm53-nvidia** | 1,486 | 102 | **6.9%** | **27.7h** |
| glm53flash-nvidia | 173 | 59 | 34.1% | 2.7h |
| kimi-k3-moonshot | 3,102 | **0** | **0.0%** | 0h（无 Key） |
| deepseek-v4.1-flash-sensenova | 63 | **0** | **0.0%** | 0h（403） |

**超时 3,349 次 × 均 65.9 秒 = 61.3 小时纯等待，其中 60.9 小时（99.2%）在 NVIDIA。**

### 关键反证：NVIDIA 根本不是必需的

我原本以为 NVIDIA 是 zk-k3 的兜底。数据否掉了：

```
zk-k3 请求 1,785 条，碰过 nvidia 的只有 3 条，且 3 条都成功。
```

而 `kimi-k3-nvidia` 的 2,967 次尝试几乎全来自 **zk-auto**（它的 targets 含 kimi-k3，
展开成 sensenova → moonshot → nvidia 三跳）。

**代价 63 小时，换来 194 次成功响应，而其中真正"只有它能救"的只有 3 次。**

### 结论

- `kimi-k3-moonshot`：**幽灵部署**，无 Key，产生 3,102 次 `no_available_credential`
  噪音（全站 5,496 次 503 的大头）。应该 `enabled: false`。
- `deepseek-v4.1-flash`：**403 permission_denied，53 次尝试 0 成功**——账号没有这个
  模型的权限。应该 `enabled: false`。
- 三个 NVIDIA 部署：把 timeout 从 60s 降到 20s 可省约 **36.8 小时**；直接禁用省 63h，
  代价是 3 条 zk-k3 请求可能失败。

## 2. 逐功能审查

### 2.1 `agent_auto` 形状改写（tool-turn → zk-long）　**有效**

要解决的问题：机械轮次占用旗舰模型。数据：`zk-long` 承接 979 条，`zk-auto` 29,590 条。

`zk-auto` 的输入输出比 **28:1**，`zk-long` **9:1**——机械流量的输出占比确实更高
（更像真实对话而非重读），分流方向正确。

但**收益无法量化**：没有"改写前 vs 改写后同流量对比"的干净样本。属"方向对、幅度未知"。

### 2.2 `front_model` 接口模型　**机制有效，但你选的模型是死的**

机制本身按设计工作（`front_model=step-5-preview` 在 06:42 重启后确实生效，
26 条日志全是 step-5）。但暴露两个问题：

**(a) 你后来在控制台改成了 `deepseek-v4.1-flash`，而它是 403 死的（0/53 成功）。**
所以"接口模型"现在不是真正在答的那个——每个请求先撞它 0.6 秒再往下走。

**(b) 这是我这个功能的真实缺陷：`_promote_front_model` 只检查"能力门槛是否通过"
（`candidate.eligible`），完全不看健康度。** 一个 0% 成功率的部署照样是 eligible，
照样被提到第一位。我写这个功能时的目标是"让真能答的模型先答"，而它没有能力
分辨"能不能答"。

**修法建议**（未实施，需你定）：把前端模型与 `Scheduler._credentials_for` 的健康
判断挂钩；或在控制台别名表直接标注接口模型的当前可用性，让运营者立刻看到自己
选的是死模型。

### 2.3 429 冷却范围 `throttle_scopes`　**方向对，但无证据证明有效**

我把它从 `provider` 改成 `account`（依据：同刻账号 04/05 在烧、其余 429，桶按账号分）。

**对抗性检验失败**：我本想用"每请求尝试次数"验证（改宽了应该变多、改准了应该变少）：

```
09-26  请求 12,727  每请求 1.01 次     ← 我的改动之前
09-27  请求  2,427  每请求 1.14 次
09-28  请求    868  每请求 1.70 次     ← 我的改动之后
```

**改后反而变高了。** 但 09-28 只有 868 条请求、且消耗器正在满速烧（样本被污染），
所以这个对比**不成立**——它既不能证明变好，也不能证明变坏。

**诚实结论：改动方向有依据，但有效性未被验证。** 我当时说"19.7% 空转是它造成的"
是把消耗器自身的空转算到了网关头上，属于归因错误。

### 2.4 墙钟预算 `ZKAI_MAX_REQUEST_SECONDS=300`　**没救到它要救的案例**

这是最该被自我否定的一条。

我写它的动机是那次"十几分钟无响应"。实测那次请求的尝试序列：

```
1.2s(429) + 0s(无凭据) + 60.3 + 60.3 + 60.4 = 182.2s 全失败
第 6 次成功 +48.5s
总墙钟 ≈ 230.7s
```

**230.7s < 300s，预算根本不会触发。** 它拦的是"20 次 × 60s = 20 分钟"那种更坏的情况
——真实存在，但**不是**这次事故。我当时说它是"直接解药"是过度宣称。

真正该做的是**不让单次尝试等 60 秒**（见 §1），而不是加一个总时长上限。

### 2.5 历史裁剪　**目标正确，但被我自己关掉了**

数据给出的最强信号：

| 别名 | 请求 | 输入 token | 输出 token | 比 |
|---|---|---|---|---|
| **zk-k3** | 1,785 | **450,658,100** | 559,973 | **805:1** |
| zk-auto | 29,590 | 364,125,100 | 13,173,383 | 28:1 |

单请求输入规模：

```
<20k      27,619 条  均输入      555
20k-100k   2,012 条  均输入   58,966   均输出 237
100k-300k  1,914 条  均输入  160,297   均输出 229
>300k        840 条  均输入  448,521   均输出 303
```

**840 条请求每条平均喂 448,521 输入 token、只产出 303 输出 token。** 这是 Codex
每轮重发全部历史。按 K3 的 ¥20/MTok 折算，仅 zk-k3 这 4.5 亿输入就 ≈ ¥9,000 等价成本。

全站等价成本 **$2,200**，输入 8.18 亿 vs 输出 1,400 万（58:1）。

**我建了 `history.py`、写了 17 个测试，然后因为"可能改变答案"把它默认关了。**
而它是唯一直接命中这个 58:1 结构的机制。这不是错——删上下文确实有风险——但意味着
**最大的一块钱没动**，我却花了几轮在 $0 的路由重排上。

### 2.6 费率校准　**有效，且刚被我自己的 bug 抹掉又救回**

`_rate_fields()` 修的是真 bug（长命进程覆盖外部校准）。修复后重算 K02 = 495,042，
与你给的真值 495,085 差 43（0.009%）。这条是扎实的。

### 2.7 404 提示　**有效但微小**

只影响 2 次请求。价值在于"下次不再猜"，不产生流量收益。

### 2.8 `max_retries` → `AsyncHTTPTransport`　**接线正确，但方向可能反了**

NVIDIA 实测 `max_retries=0`（我接的）。但超时是**读超时**，连接级重试救不了。
真正的问题是 60s 太长（见 §1）。**这条改动是对的，但对主要病症无效。**

### 2.9 消耗器饥饿救济　**完全无效**

```
K03/K06/K07/K08/K09 本周已烧 ≈ 0 / 540,000
全站本周 2,160,092 / 4,860,000 = 44%
```

5 个账号连续 14 小时 0 产出，日志每期都是"借出后仍被限流，收回救济额度"。
救济上限 `starve_boost >= 2`（借 1~2 级并发）对得住 16 并发的既得账号毫无胜算。

**这个机制的存在制造了"已经在处理了"的错觉，实际产出为零。**

## 3. 我这几轮改动的自我评分

| 改动 | 声明的作用 | 实证结论 |
|---|---|---|
| 429 范围 provider→account | 消除 19.7% 空转 | **归因错误，效果未验证** |
| 墙钟预算 300s | 治"十几分钟无响应" | **不触发，没救到** |
| front_model | 让能答的模型先答 | **机制对，但无健康检查，你选的是死模型** |
| tool-turn 改写 | 机械轮别占旗舰 | 方向对，幅度未知 |
| 费率校准 | 让预算对齐现实 | **有效**（数值吻合 0.009%） |
| 404 提示 | 少猜 | 有效但影响 2 条请求 |
| 历史裁剪 | 省历史重发 | **目标最准，但我把它关了** |

**七个里只有一个有硬证据（费率校准）。** 这不是自谦，是数据。

## 4. 按"每小时等待/每块钱"排序的行动清单

1. **禁用幽灵与死掉的部署**（零风险，立刻见效）
   - `kimi-k3-moonshot`：无 Key → `enabled: false`
   - `deepseek-v4.1-flash`：403 → `enabled: false`（**顺便解决你接口模型选错的问题**）
2. **NVIDIA 三部署：timeout 60s → 20s，或直接禁用**（省 36.8h ~ 63h）
3. **把接口模型换成真能答的**（`step-5-preview`，99.8% 成功率）
4. **给 `front_model` 加健康检查**，或至少在控制台显示它的可用性
5. **认真评估打开历史裁剪**（命中 58:1 结构，是唯一的成本大头）
6. **要么修好消耗器的饥饿救济，要么删掉它**——现在它只是让日志看起来在干活

## 5. 我认为"合理且有效"的、不需要动的东西

- **能力路由 + `capability` 策略本身**：`step-5-preview` 在 zk-auto 里赢下 94% 是
  因为它真的最合适（99.8% 成功率、8.6s 延迟）。这不是"路由失效"，是路由工作正常。
- **429 → 冷却 → 故障转移的基本盘**：7,727 次 429 平均 822ms 快速失败，没有卡住。
- **凭据池状态机**：14/15 可用、0 冷却、0 不健康，是稳的。
- **`agent_auto` 的"改写发生在候选展开之前"**：这个顺序保证长链上捞不回 K3，
  设计是对的（`zk-long` 的 targets 里根本没有 kimi-k3）。
