## 2. 诊断结论（附证据）

### 2.1 中断：不是代码回归，是容量打满 + 一个客户端的心跳盲区

服务器 HEAD = 本机最新 `7c89c0b`（实施前），工作区未提交改动只碰可观测性面板，
不碰请求链路。现役服务器 11-26 请求记录（`/var/lib/zkai/zkai.db`，只读）：

| 时段 | 成功 | error | cancelled |
|---|---|---|---|
| 04:00 | 98 | 0 | 0 |
| 05:00 | 133 | 4 | 15 |
| 06:00 | 89 | 6 | 14 |
| 07:00 | 69 | 5 | 12 |
| 08:00 | 14 | 19 | 0 |
| 09:00 | 7 | 11 | 0 |
| 10:00 | 9 | 0 | 14 |

- 55 条 cancelled **全部** UA `undici`、HTTP 499、`error_type=no_stream_meta`、平均 58.2s。
- 其中 **10 条零上游尝试**（`request_attempts` 无对应行）、耗时整齐落在 **59.74~59.92s**。
- 7 天 error_type：`no_available_credential` 951、`rate_limit_error` 879、`no_stream_meta` 451。
- 一条典型 499 的 attempt 链：商汤 3 把 Key 依次 429 → ModelScope "无可用 Key（34815s 后恢复）"
  → 无首块 → `meta=None` → `request_service.py` 记 `no_stream_meta` → 客户端 58s 后断开。

**推断的因果链**：
上游额度打满 → 调度器在预取窗口内反复故障转移、迟迟不给首字节 →
预取窗口 10s 到点返回 200，但 `undici` 不在心跳白名单（`app/api/chat.py` 的
`_PING_USER_AGENTS`），于是 `ping_every=None` → `asyncio.wait(..., timeout=None)` 纯等、
零字节 → 客户端 60s 硬超时断开。

**关键旁证**：11-23 的文档判断「undici 不依赖心跳」，本次数据推翻——服务器上 2490 条
undici 请求，它恰恰是 499 的唯一主体。WorkBuddy / ZCode / qoder 都是独立 UA 字符串、
不是 undici 子串，所以补 undici 不会污染 WorkBuddy（WorkBuddy 会把 `: ping` 当正文显示）。

### 2.2 "只调用一家"：一半是设计，一半是真缺陷

四层抽象：`Provider → Deployment → Model → Alias`。一个 deployment =
(provider, 上游 model) 对，是故障转移最小单位。多个 deployment 组成**有序候选链**，
一次请求只走一条、前面挂了才试后面——这是设计，不是 bug。单请求并行 fan-out 会
双倍烧配额、结果不一致，**明确不做**。

但"加了供应商却顶不上用"有三个真机制缺口：

1. **策略层（决定性）**：`router.py:305` 的优先级是 `alias.strategy > model.strategy > 默认`。
   `ds` 别名是 `priority`，把 `deepseek-flash` 模型配的 `round_robin` 完全盖掉，
   链首永远是 `a-ds`(AMD)；`zk-auto` 虽是 `round_robin`，但 `front_model: deepseek-flash`
   每轮把它提到队首。
2. **健康层（次要）**：`unavailable_deployments()` 只用于 `_promote_front_model`，
   没传给 `strategy.order()`——额度耗尽 9.7h 的腿仍排队首，被调度器跳过后白费首跳。
3. **可用性层（比策略更要命）**：多供应商里混进了 NVIDIA 死腿。11-26 该腿 14 次尝试、
   0 成功、全 33~59s 挂死（AGENTS.md 早有 NVIDIA 账号级失效的结论）。
   10:28 后 `k3.1p` 的 5 次调用全打 nvidia、5 次全 cancelled，modelscope 腿一次没上。

**现网配置真相**（实施前，服务器 `/zkadmin/models` 内存态 + YAML + DB 镜像三处一致）：

| 模型 | 部署数 | 供应商 | strategy |
|---|---|---|---|
| `deepseek-flash` | 3 | sensenova / AMD / modelscope | round_robin |
| `k3.1p` | 2 | nvidia / modelscope | round_robin |
| 其余 5 个 | 各 1 | — | — |

⚠ 注意：本机 `config/models.yaml` 是**旧快照**（`ds` 别名 3 个 targets），服务器现网
`ds` 只有 1 个 target（`deepseek-flash`），多供应商是**同一模型的多个 deployment**。
以服务器为准。

## 3. 实施方案（已实施）

设计目标：把静态故障转移列表升级成**活的供应商池**——平时分担（多家轮流接活）、
出事互备（健康的顶上）、全程可见。

### P1 中断修复

| 改动 | 位置 | 说明 |
|---|---|---|
| `undici` 加入心跳白名单 | `app/api/chat.py:100-104` | 55 条 499 的直接修复。同时保留已有的 `sse_comment_user_agents` 配置通道作热更入口 |
| `cancelled` 记 `client_disconnected` | `app/services/request_service.py:424-431` | 原 `no_stream_meta` 把"客户端断开"和"没产出 meta"混成一个类型，误导排查 |
| 回写 11-23 错误结论 | `AGENTS.md`、`docs/排查过程详述.md` | 记录"名单必须靠线上 UA 原文验证" |

### P2 路由机制

1. **降权（`app/routing/strategy.py:35,132`）**：`RoutingCandidate.penalized` + 六个策略
   统一走 `_demote_penalized`——冷却/隔离的腿排到队尾但**不删除**（保留链完整性，
   避免全冷却时零候选）。`app/routing/router.py:299` 把 `unavailable` 写进候选，
   owner 是 scheduler，Router 仍不做 I/O。
2. **模型内独立轮转（`app/routing/router.py:316,402-450`）**：`_rotate_model_local_pools`
   在全局排序后，只对**同一模型占用的槽位**做组内轮转；跨模型顺序仍由别名策略决定，
   capability 全局打分语义不变。解决了 `ds` 是 priority 时 3 家仍轮流接活。
3. **防双重轮转（`router.py:439`）**：外层策略与模型策略**相同**时跳过内层补转。
   这是真机验证发现的 bug（见 §5）。

### P3 可见性

- `RequestRepository.deployment_summary()`（`app/database/repositories/request.py:230`）
  以 **`request_attempts`** 为数据源（`requests` 表 cancelled/error 的 deployment_id
  100% 为 NULL，用它算成功率会虚高；attempts 1118 行零缺失）。
- 接入 `/zkadmin/stats.deployments`（`app/api/admin/stats.py:32`），控制台模型页新增
  "各部署真实接单"表（`app/web/console.js:1494`），路由预览显示降权腿。

### P4 校验

- merge 分支补 provider 存在性与 deployment id 去重（`app/api/admin/models.py:106` 附近）。
- `scripts/check_config.py:120` 加**只读告警**：多部署跨多家供应商但未配分担策略。
  刻意**不自动改策略**——静默改策略会改变成本结构。

### 服务器现役配置（P0，单独授权后执行）

| 项 | 决定 | 依据 |
|---|---|---|
| `ds` 改 round_robin | **没做** | 新代码下 preview 已见三家轮转，冗余 |
| `zk-auto` 临时 front_model | **没动** | preview 显示三家仍轮转、未破坏分担；删除属运营决策 |
| NVIDIA 死腿 | **摘除** | `n-k3.1p` 设 `enabled: false`（保留可回滚），热加载后 `gated_out=['n-k3.1p']` |

## 4. 明确不做（边界）

- 单请求并行 fan-out 到多家（双倍烧配额、结果不一致、要合并策略）。
- 主动探测上游额度余量（上游无信号，只能靠失败冷却 + 一次性实测）。
- 静默改默认策略 / 自动改权重（会改变成本结构，且 YAML / DB 镜像同步易漏）。
- 把部署级冷却与凭据级长冷却合并成一个"健康分"（信号语义不同，后者 `b3c4d86` 已处理）。
- 默认给所有 UA 发心跳（WorkBuddy 会把 SSE 注释行当正文显示）。
- 修容量本身（补额度 / 等魔搭每日重置是运营动作，不是代码动作）。

### 5.3 真机验证（现役服务器）

- 服务器 HEAD 对齐 `a20d707`，网关 healthy、`config_watch.reload_count=2`、
  `runtime.stream_prefetch_timeout=10.0`。
- `/zkadmin/router/preview` 连续调用：
  - `ds` → `a-ds / 商汤 / m-ds` 三家轮流
  - `zk-auto` → 三家轮流
  - `k3.1p` → 摘除 NVIDIA 后只剩 `m-k3.1p` 一条腿（预期固定）
- undici UA 真实流式请求：200、1.1s、无 error，落库 `deployment=m-ds` 成功。
- `check_config.py`：无错误、0 警告。

### 5.4 实施中发现并修复的真机 bug

**双腿轮转抵消**：`k3.1p` 连续 6 次 preview 都停在 `m-k3.1p`。原因是外层
`strategy.order()` 已按 round_robin 转一次，内层 `_rotate_model_local_pools` 用同一 key
又转一次，`+2 mod 2 = 0` 回到原点。本地 3 腿测试因 `+2 mod 3 ≠ 0` 碰巧通过、
掩盖了 bug；补 2 腿回归才暴露。修复：外层策略与模型策略相同时跳过内层补转。

## 6. 待审问题（请重点检查这些）

1. **因果链是否站得住？** 55 条 499 中 10 条零尝试、59.7~59.9s，我据此推断
   "客户端 60s 硬超时 + undici 无心跳"。但服务器 journald **没有留存 05 点时段的应用日志**，
   无法坐实这 60s 具体卡在哪个 `await`。是否有其他解释（如客户端自身重试间隔）？
2. **F1 会不会有反效果？** 补心跳后客户端不再 60s 主动断，但若上游全挂，
   客户端会继续等到 `max_request_seconds=300s` 兜底——体验是否从"58 秒中断"
   变成"等 5 分钟才报错"？11-23 已把窗口外错误转成流内 error，是否足够？
3. **`_rotate_model_local_pools` 的槽位重排是否安全？** 它按 `model.id` 分组、
   记住在 `ordered` 中的位置后原地替换。若同一模型的部署在 `ordered` 中**不连续**
   （capability 全局打分交错时可能发生），这种"只重排本组槽位"的做法是否会
   破坏全局排序语义？
4. **`penalized` 降权与 `front_model` 提升的交互**：`_promote_front_model` 检查
   `unavailable` 决定不提升冷却腿；但现在降权信息在 `candidate.penalized`，
   提升逻辑仍用旧的 `unavailable` 集合——两处判据是否会不一致？
5. **`deployment_summary` 的 `started_at` 过滤**：`request_attempts.started_at`
   来自 `AttemptOutcome.started_at`（`time.time()` 浮点）。测试里必须显式传当前时间，
   默认 0.0 会被 cutoff 过滤。线上是否有 attempt 行 `started_at=0` 导致统计漏记？
6. **`credential_affinity` 与分担的冲突未解决**：会话亲和需求"同一会话钉住上次成功的 Key"
   以命中 prompt cache，跨请求轮换部署会打断缓存、抬高 prefill 成本。本方案
   **显式记录但未改变** affinity 行为。这是否会让分担的实际收益被缓存损失抵消？
7. **`front_model` 是否该摘？** `zk-auto` 的 `front_model: deepseek-flash` 是 11-23 23:15
   的临时措施，YAML 注释自己写了"还原只需改回 k3.1p"，已挂 3 天。preview 显示
   它未破坏模型内轮转，所以我没动。但长期钉住一个模型是否违背"分担"初衷？
8. **摘除 NVIDIA 腿是否过于激进？** 14 次尝试 0 成功、全 33~59s 挂死，证据充分；
   但 NVIDIA 账号权限问题理论上可能恢复。采用 `enabled: false` 而非删除、保留
   `.bak`，回滚成本是否足够低？是否有更好的"自动隔离"路径（quarantine 阈值 3 次）
   本可以直接接管、不需要人工摘除？
