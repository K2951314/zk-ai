| 复审发现 | 严重度 | 处置 |
|---|---|---|
| **「六个策略统一走 `_demote_penalized`」不成立**：只有 priority / capability 调了，round_robin / weighted / cost / speed 四个没调。线上 `zk-auto` 恰是 round_robin，**降权在主链路上从未生效** | 高 | 已修：降权收敛到 `_number`（六个策略的唯一出口），见 P5 |

| 文档缺**效果判据**：只验证了「preview 里三家轮转」，没有定义「怎么算分担真的生效」 | 中 | 已补 §8 观察指标 |

**第一性原理复核**：客户端要的不是「连接不断」，而是「尽快拿到内容，或尽快拿到
可操作的错误」。心跳只把「静默断连」换成「静默等待」，它是**必要条件不是方案**；
多供应商池的价值 = 分担 + 互备，其成立前提是**健康判据必须作用于每一条排序路径**——
路由计划与调度器执行一旦各说各话，所有策略层工作都归零。本次三处修复都收敛到
这同一条不变量：**路由计划 = 调度器将执行的顺序 = 日志里报的顺序**。
另一条不变量同样要记住：**路由只能减少浪费，不能创造容量**（§8）。

## 2. 诊断结论（附证据）

### 2.1 中断：不是代码回归，是容量打满 + 一个客户端的心跳盲区

服务器 HEAD = 本机最新 `7c89c0b`（实施前），工作区未提交改动只碰可观测性面板，
不碰请求链路。现役服务器 11-26 请求记录（`/var/lib/zkai/zkai.db`，只读）：

| 时段 | 成功 | error | cancelled |
|---|---|---|---|
| 04:00 | 98 | 0 | 0 |
| 05:00 | 133 | 4 | 15 |
| 06:00 | 89 | 6 | 14 |
| 07:00 | 69 | 5 | 12 |
| 08:00 | 14 | 19 | 0 |
| 09:00 | 7 | 11 | 0 |
| 10:00 | 9 | 0 | 14 |

- 55 条 cancelled **全部** UA `undici`、HTTP 499、`error_type=no_stream_meta`、平均 58.2s。
- 其中 **10 条零上游尝试**（`request_attempts` 无对应行）、耗时整齐落在 **59.74~59.92s**。
- 7 天 error_type：`no_available_credential` 951、`rate_limit_error` 879、`no_stream_meta` 451。
- 一条典型 499 的 attempt 链：商汤 3 把 Key 依次 429 → ModelScope "无可用 Key（34815s 后恢复）"
  → 无首块 → `meta=None` → `request_service.py` 记 `no_stream_meta` → 客户端 58s 后断开。

**推断的因果链**：
上游额度打满 → 调度器在预取窗口内反复故障转移、迟迟不给首字节 →
预取窗口 10s 到点返回 200，但 `undici` 不在心跳白名单（`app/api/chat.py` 的
`_PING_USER_AGENTS`），于是 `ping_every=None` → `asyncio.wait(..., timeout=None)` 纯等、
零字节 → 客户端 60s 硬超时断开。

**关键旁证**：11-23 的文档判断「undici 不依赖心跳」，本次数据推翻——服务器上 2490 条
undici 请求，它恰恰是 499 的唯一主体。WorkBuddy / ZCode / qoder 都是独立 UA 字符串、
不是 undici 子串，所以补 undici 不会污染 WorkBuddy（WorkBuddy 会把 `: ping` 当正文显示）。

### 2.2 "只调用一家"：一半是设计，一半是真缺陷

四层抽象：`Provider → Deployment → Model → Alias`。一个 deployment =
(provider, 上游 model) 对，是故障转移最小单位。多个 deployment 组成**有序候选链**，
一次请求只走一条、前面挂了才试后面——这是设计，不是 bug。单请求并行 fan-out 会
双倍烧配额、结果不一致，**明确不做**。

但"加了供应商却顶不上用"有三个真机制缺口：

1. **策略层（决定性）**：`router.py:305` 的优先级是 `alias.strategy > model.strategy > 默认`。
   `ds` 别名是 `priority`，把 `deepseek-flash` 模型配的 `round_robin` 完全盖掉，
   链首永远是 `a-ds`(AMD)；`zk-auto` 虽是 `round_robin`，但 `front_model: deepseek-flash`
   每轮把它提到队首。
2. **健康层（次要）**：`unavailable_deployments()` 只用于 `_promote_front_model`，
   没传给 `strategy.order()`——额度耗尽 9.7h 的腿仍排队首，被调度器跳过后白费首跳。
3. **可用性层（比策略更要命）**：多供应商里混进了 NVIDIA 死腿。11-26 该腿 14 次尝试、
   0 成功、全 33~59s 挂死（AGENTS.md 早有 NVIDIA 账号级失效的结论）。
   10:28 后 `k3.1p` 的 5 次调用全打 nvidia、5 次全 cancelled，modelscope 腿一次没上。

**现网配置真相**（实施前，服务器 `/zkadmin/models` 内存态 + YAML + DB 镜像三处一致）：

| 模型 | 部署数 | 供应商 | strategy |
|---|---|---|---|
| `deepseek-flash` | 3 | sensenova / AMD / modelscope | round_robin |
| `k3.1p` | 2 | nvidia / modelscope | round_robin |
| 其余 5 个 | 各 1 | — | — |

⚠ 注意：本机 `config/models.yaml` 是**旧快照**（`ds` 别名 3 个 targets），服务器现网
`ds` 只有 1 个 target（`deepseek-flash`），多供应商是**同一模型的多个 deployment**。
以服务器为准。

1. **降权（`app/routing/strategy.py:35,132`）**：`RoutingCandidate.penalized` +

2. **模型内独立轮转（`app/routing/router.py:316,402-450`）**：`_rotate_model_local_pools`

   capability 全局打分语义不变。解决了 `ds` 是 priority 时 3 家仍轮流接活。
3. **防双重轮转（`router.py:439`）**：外层策略与模型策略**相同**时跳过内层补转。
   这是真机验证发现的 bug（见 §5）。

## 4. 明确不做（边界）

- 单请求并行 fan-out 到多家（双倍烧配额、结果不一致、要合并策略）。
- 主动探测上游额度余量（上游无信号，只能靠失败冷却 + 一次性实测）。
- 静默改默认策略 / 自动改权重（会改变成本结构，且 YAML / DB 镜像同步易漏）。
- 把部署级冷却与凭据级长冷却合并成一个"健康分"（信号语义不同，后者 `b3c4d86` 已处理）。
- 默认给所有 UA 发心跳（WorkBuddy 会把 SSE 注释行当正文显示）。
- 修容量本身（补额度 / 等魔搭每日重置是运营动作，不是代码动作）。

## 6. 待审问题与复审结论

> 原 8 个待审问题保留题干（精简），每条下面是第二轮复审**逐行读码后的结论**。
> 涉及文件：`router.py` / `strategy.py` / `scheduler.py` / `chat.py` /
> `request_service.py` / `repositories/request.py`。

1. **因果链是否站得住？** 55 条 499 中 10 条零尝试、59.7~59.9s，但 05 点时段应用日志没留存。
   **复审结论：成立，但证据强度要分级。** 硬证据是 DB（55 条 499 全部 undici、
   10 条零上游尝试、耗时 59.74~59.92s）；「客户端 60s 硬超时」是强推断；
   「这 60s 全部卡在预取窗口」**没有坐实**——零尝试的那 10 条也可能耗在
   `_wait_for_credential`（上限 10s）与凭据冷却里。修复不依赖这个区分：
   undici 进白名单 + 预取超时发心跳，对两种卡点都有效。
   **教训：应用日志不留存，排查就永远只能靠 DB 猜**——这比多一个推断更要命。

2. **F1 会不会从「58 秒中断」变成「等 5 分钟才报错」？**
   **复审结论：风险比原估计小，但旋钮要写清楚。** 代码事实：所有候选都在
   冷却/隔离时，调度器直接跳过并立刻 `_exhausted`，**不会**等满
   `max_request_seconds`；11-23 的流内 error 事件保证 200 已发出后客户端仍能
   收到错误。真正会拖到 300s 的是「每家都有 Key、每家都在失败」——那是
   **慢失败**而非**无错误**，由 `attempt_timeout_floor/margin` + 墙钟预算兜底。
   建议把 `max_request_seconds` 当体验旋钮写进运维手册：要快失败就调小，
   别默认 300s 不可动。心跳解决的是「静默」，从来不是「容量」。

3. **`_rotate_model_local_pools` 的槽位重排是否安全？**
   **复审结论：安全，但「capability 全局打分语义不变」必须限定为「跨模型」。**
   实现只重排同一 `model.id` 占用的槽位，跨模型相对顺序不变；代价是**模型内部**
   不再按 capability 分数排先后——而这正是模型显式配 `round_robin`/`weighted`
   时运营者要的行为，未配这两个策略的模型完全不受影响。轮转只作用于健康腿，
   penalized 腿留在队尾原槽位，不会被转回首跳。

4. **`penalized` 降权与 `front_model` 提升的判据会不会不一致？**
   **复审结论：这个不一致不存在——两者同源。** `candidate.penalized` 就是
   `deployment.id in unavailable`，`_promote_front_model` 用的也是同一个
   `unavailable` 集合。**真正的不一致在别处**：四个策略没降权、兜底路径丢工序
   （见 P5）。教训：怀疑两处判据漂移时，先检查是不是存在**第三条根本没走
   这套判据的路径**，而不是对比两处同源代码。

5. **`deployment_summary` 的 `started_at` 过滤会不会漏记？**
   **复审结论：线上无此数据，但默认值是真陷阱，已修。** 调度器所有
   `_attempt_outcome` 调用都显式传 `time.time()`（含无凭据的空尝试），线上不会
   出现 `started_at=0`。默认值 `0.0` 对任何新调用方都是静默吞数据的坑，
   已改为当前墙钟并加回归测试（P5）。

6. **`credential_affinity` 会不会抵消分担收益？**
   **复审结论：现状已是正确折中，不需要改代码。** 粘性只在**同一会话的后续
   轮次**生效（`_apply_deployment_affinity` 在 plan 之后把上次成功的部署提前），
   新会话首轮仍走模型内轮转。即**跨会话分担、会话内省 prefill**，分担收益没有被
   抵消。要补的是度量不是逻辑：按部署看 `usage` 日志的 `cached=` 命中率，
   确认缓存收益确实大于分散的损失（判据见 §8）。

7. **`front_model` 是否该摘？**
   **复审结论：保留，但要从「临时措施」改成「有复审周期的配置」。** 它不破坏
   模型内轮转（提升的是该模型当前轮到的健康部署），与分担不冲突；真正的代价是
   **跨模型分担失效**——`zk-auto` 的其他模型因此长期接不到机械流量。这是运营
   决策不是代码缺陷：给它一个明确的复审日期，到期要么删掉、要么写成正式配置，
   别让 YAML 注释里的「还原只需改回 k3.1p」一直挂着。

8. **摘除 NVIDIA 腿是否过于激进？**
   **复审结论：不过激，回滚成本足够低。** 自动隔离（阈值 3 次、阶梯封顶 6h）
   确实能接管，但每个隔离窗口结束都会放一次半开请求进来；NVIDIA 这种
   「100% 挂死 33~59s」的腿意味着**周期性白等一分钟**。`enabled: false` 消除了
   这个损耗，回滚只是改回 true（热加载自动生效），`.bak` 仍在。自动隔离继续
   作为无人值守时的兜底，两者不矛盾。

## 8. 复审补的效果判据与未竟事项

原方案只验证了「preview 里三家轮转」，没有定义「怎么算分担真的生效」。
**没有判据的上线等于没验证**，补四条（数据源都已存在，不需要新代码）：

| 判据 | 看什么 | 异常时先查什么 |
|---|---|---|
| 分担是否生效 | 24h 内 `request_attempts` 按 deployment 的 attempts 分布（控制台「各部署真实接单」）。单家长期 >80% 就是没分担起来 | 先查 affinity（同会话粘性是预期行为）与 `front_model`，再查策略配置 |
| 中断是否收敛 | 按 UA 统计 499 / `client_disconnected`，undici 应趋近 0；`no_stream_meta` 只剩非取消场景 | 心跳白名单是否与线上 UA 原文匹配（这条已经错过两次） |
| 该不该加容量 | `no_available_credential` + `rate_limit_error` 占比持续高位 | **加账号 / 充值 / 分流**，不要再调路由——路由只能减少浪费，不能创造容量 |
| 分担的缓存代价 | 按部署的 `cached_tokens` 命中率，对比直连基线 | 命中率显著更低说明在烧 prefill，考虑缩小轮转池或拉长 affinity TTL |

**刻意不改、留作后续**（避免把行为变更混进修复）：

- `RoundRobinSelection` 游标按 `eligible[0].model.id` 记，多模型别名混排时游标
  语义粗糙（单模型池不受影响）。改它属于行为变更，需要单独评估与测试。
- ~~`deployment_summary.success_rate` 的分母是尝试次数，若要请求级口径需另起聚合。~~
  **2026-11-26 已补**：返回新增 `requests`（`count(distinct request_id)`），控制台
  「请求 / 尝试」两列并排，成功率明示为「成功尝试 ÷ 尝试次数」。
- ~~多模型 + 同策略叠加时仍值得补一组端到端用例。~~
  **2026-11-26 已补并在现状代码上验证通过**：
