# 反代战略评估：WorkBuddy 类桌面版的正确打开方式（2026-11-08）

## 0. 起因

运营者看到网上有人「反代 WorkBuddy 的积分和免费模型」，质疑此前
「操作桌面版」（反向桥接 worker、chatgpt_service 配置外科手术）是否走了误区：
如果能反代，直接反代是不是更简单、更高效？

本文用本机实测事实回答，结论先行：**直觉对了一大半，但要把「用桌面版」的
三个动机拆开——为了「模型额度」操作桌面版确实是绕远；为了「工具」和「已有
会话」桌面版不可替代。而所谓反代，在本项目里不是新机制，是给现有供应商
多加一把凭据。**

## 1. 实测事实（2026-11-08 侦察，全程只读、未回显任何密钥）

### 1.1 WorkBuddy 的「免费模型」上游身份（~/.workbuddy-ai/logs 提取）

| 上游 | 性质 | 网关现状 |
|---|---|---|
| `https://api-inference.modelscope.cn/v1/` | OpenAI 兼容 | **已直连**（魔搭供应商，现役） |
| `https://api.stepfun.com/step_plan/v1` | OpenAI 兼容（step_plan 专属路径） | **已直连**（step-5-preview 是现役接口模型） |
| `https://copilot.tencent.com` | 腾讯 Copilot（协议未探） | 未接 |

**这就是「反代」的真相**：WorkBuddy 是 CodeBuddy 家族产品（更新包、频道库全走
codebuddy.ai / 腾讯 COS），它的免费模型来自魔搭 / StepFun / 腾讯 Copilot 的
**OpenAI 兼容 API**。所谓反代 = 拿 WorkBuddy 的订阅 token 直接打这些上游，
不经过桌面版界面。

### 1.2 凭据存放（决定提取成本）

- `~/.workbuddy-ai/security/<user-id>`、`keyblob`：加密 blob（附录 E 同款结论：
  敏感凭据不落明文）。
- `cli-env/wecom-cli.sh`：只发现企业微信 CLI 的环境注入，无模型凭据。
- `sessions/*.json`：只有 url/pid/sessionId，无凭据（与附录 E 一致）。

→ **token 提取是唯一未知数**。可行路径按成本排序：①mitmproxy 抓一次桌面版
请求看 Authorization 头（一次性，半天内）；②读 app 内存/asar 源码找解密入口
（成本不可控）；③放弃。

### 1.3 附录 E/F 已有结论的适用范围（不变的部分）

- 桌面版**本地服务**（ACP 58232/51489 等）：网关密码每次启动随机生成不落盘
  → 直连不可行，**反向桥接仍是驱动桌面版 agent 的唯一正路**（E.3）。
- **editor_sdk 39099 免鉴权 MCP、231 个工具**：表格/文档/幻灯片操作，
  这是桌面版作为「工具」的价值，反代替代不了。
- 端口每次启动会变（F.1 硬结论）：任何写死端口的实现都会碎。

## 2. 判定：误区在哪、不在哪

「操作桌面版」混了三个动机，拆开后误区自动显形：

| 动机 | 正确路径 | 桌面版是否必要 |
|---|---|---|
| **用它的模型额度/免费模型** | 反代上游 API（= 加凭据） | ❌ 不必要，桌面版只是这些上游的普通客户端 |
| **用它的工具**（Office/编辑器 231 工具） | editor_sdk MCP → 执行体 | ✅ 必要（工具跑在桌面版进程里） |
| **用它的已有会话/上下文** | ACP 反向桥接（附录 E） | ✅ 必要（密码只在它启动的子进程里） |

所以「进入了误区」只对第一行成立——而且当时其实没碰到这行：
chatgpt_service 是让桌面版 Codex **用我们的网关**（入站），反向桥接是**驱动
桌面版干活**（工具/会话）。真正绕远的风险在「为额度而驱动桌面版」这个想法上，
它还没被实施过，今天刚好砍掉。

## 3. 架构结论：反代在本项目里是「加一行配置」，不是「一套新系统」

网关的本职就是协议枢纽，两个方向的先例都已存在：

```
入站（已有）：ZCode / Codex桌面版 / Qoder自定义模型 ──→ zkai 网关
出站（已有）：网关 ──→ 商汤×9 / 魔搭 / StepFun / NVIDIA(隔离兜底)
出站（新增）：网关 ──→ StepFun/魔搭(+WorkBuddy订阅token)   ← 今天讨论的「反代」
```

关键洞察：**上游已经是现役供应商，反代接入 = 给 providers.yaml 的
stepfun/modelscope 各加一把凭据**，随后整套餐老机制原样生效：

- 按**账号**分桶的 tpm/rpm 闸（商汤 9 把 Key 的教训直接复用）；
- 部署级自动隔离（连续 3 次失败即屏蔽——token 被轮换/封禁就是一次普通故障）；
- 墙钟预算、故障转移、用量记账；
- 零新适配器代码（OpenAI 兼容；step_plan 路径差异由 base_url 吸收）。

对比被否决的路：反向桥接要 worker 进程、ACP 协议、随机密码传递、
writer_occupied 独占处理——**复杂度差一个数量级**。运营者的直觉正确。

## 4. 分期计划

### R0 侦察（半天，先验证再动手）

一次 mitmproxy 抓包桌面版 → 回答三个问题：①token 在哪个头、什么格式；
②step_plan 路径的鉴权与普通 /v1 是否同源；③token 轮换频率（重启换不换）。
产出一份实测记录进 docs/。**超过半天拿不到 token 就放弃**——机会成本是
cli_usage 账本（比这个杠杆更大）。

### R1 接入（半天，依赖 R0 成功）

- providers.yaml：stepfun/modelscope 各加 `wb-*` 凭据，注释标注
  「来源：WorkBuddy 订阅复用，提取日期、ToS 风险自负、预期寿命未知」；
- token 进 `.env`（密钥红线）；
- **不进 zk-auto/zk-long 主链**，先做点名模型（如 `wb-free/*` 或直接点名
  step 模型指定凭据）；额度按账号独立分桶；
- 自动隔离兜底已内建，无需新代码。

### R2 收缩桌面运维面（与 R1 并行，各半天）

- `chatgpt_service.py`（655 行）从网关核心拆为
  `scripts/setup_codex.py` 一次性配置工具（对抗式审查 2026-11-08 的
  架构债 #8 落地）——配置外科手术是 setup 期的事，不该常驻网关进程；
- 反向桥接 worker（附录 E.6）**降优先级**：只为「已有会话上下文」场景服务，
  不再作为模型额度的通道被考虑。

### R3 工具面（按总控大脑原计划）

editor_sdk MCP 接成 `backend: mcp` 执行体（附录 F 已规划，先只读工具）。
这跟反代无关，是桌面版真正的不可替代价值。

## 5. 脆弱凭据纪律（新增规矩，写进 providers.yaml 注释）

1. 订阅复用类凭据**永不进默认故障转移链**（zk-auto/zk-long），只点名调用；
2. 每把凭据标注提取日期与来源，token 失效按普通故障隔离，不修配置去追；
3. ToS 风险自负立场沿用免费档执行体文档的先例（2026-10-25）；
4. 这类供应商的用量必须进 cli_usage 账本——**「白嫖了多少」要是个数字，
   不能是感觉**。

## 6. 战略视角：额度复利

手里已有的池子：商汤 9 账号（12 万/5h）、魔搭、StepFun、CodeBuddy/Qoder/Gemini
免费档、WorkBuddy 订阅（R1 后）。它们全是**同一张额度账本上的行**。
总控大脑 P0「动态选执行体」的打分输入正是「哪个池子此刻有余量」——
反代接入让账本多一行，而不是多一套机制。这也是判断「值不值得做」的标尺：
**凡是给账本加行的接入都便宜，凡是另起炉灶的接入都贵。**

## 7. R0 实测结果（2026-11-09 执行）：静态提取失败，负结论归档

按 §4.R0 的止损规则执行了一轮穷尽式静态侦察（全程只读、凭据只验形状不回显），
**客户端侧不存在可直接提取的上游 token**。证据链：

| 静态源 | 结论 |
|---|---|
| `traces/`（1 GB） | 只是 agent 工作流 span 与提示词内容——连本项目自己的商汤排障文档都被它读进去了；**不是 HTTP 线缆日志** |
| `workbuddy.db` / `edge-sync-mapping-v4.db` | 表只有 sessions/workspaces/automations/usage，无凭据列 |
| `keyblob`（336 B） | 不是 DPAPI，是 AtRestEncryption 信封：`{"version":1,"keyId":…,"slots":[{"type":"static-v1",…wrapped}]}` ——解包算法在 `app.asar.unpacked/cli/dist/codebuddy-lite-wb.mjs`，需逆向密钥派生（估 1–2h） |
| `security/<user>/` | cipher/data 全是 0 字节空壳 |
| `plugin-account-state` / `user-state` / `settings` / `connectors` / `app/users` | 只有插件开关与偏好，无凭据形键 |
| `~/.codebuddy/`（CLI 家） | 无 credentials/auth 文件 |
| LevelDB（两处）+ Windows 凭据管理器 | 无 JWT、无 sk- 形状、无相关条目 |

**两个改写判断的事实**：

1. **WorkBuddy 的模型调用走腾讯中转聚合**（进程 TCP 连接全部指向腾讯云边缘段，
   无直连 modelscope/stepfun 的出站连接）——日志里那些 modelscope/stepfun
   URL 是提示词内容（agent 读过项目文档），不是真实流量目标。
   → 反代的目标从「OpenAI 兼容直连」降级为「copilot.tencent.com 中转面」，
   协议未知、配额在服务端按账号计量，价值大幅缩水。
2. WorkBuddy = 套壳 codebuddy-code CLI（`app.asar.unpacked/cli/` 里的
   `codebuddy-lite-wb.mjs` + product 配置），其上游鉴权在腾讯后端，
   客户端只持有中转会话凭据（且被 static-v1 加密）。

**判定**：静态路径宣告失败并归档。剩余两条路都不符合「加一行配置」的便宜标准：

- mitmproxy 实时抓包（需运营者在场配合跑一次桌面版请求 + 装信任证书），
  且抓到的预期是中转会话 token，不是上游直连 key；
- 逆向 static-v1 解包算法（1–2h），产出同上。

**结论升级**：R1（加凭据接入）对 WorkBuddy **不划算**，止损。
「反代」战略对 WorkBuddy 的最终形态是：**把它当作 codebuddy 执行体的一个
登录态来源**——项目现役的 `cli-codebuddy` 执行体（免费档、
`deepseek-v4.1-flash` 实测 $0.0000）已经是这条通道的官方形态，
额度账本上它那一行已经存在。WorkBuddy 桌面版剩下的独有价值只有两块：
editor_sdk 的 231 个工具（R3）和已有会话上下文（附录 E 反向桥接）。

> 战略标尺回头看依然成立，只是结论反转：**WorkBuddy 反代不是「加一行」，
> 是「另起炉灶」——所以不做。** 真正便宜的「加一行」是 `cli_usage` 账本
> （把现有各池子的用量先记起来），维持它为下一优先级。

## 8. 群友工具解剖（2026-11-09）：§7 的两处误判被推翻，结论再反转

运营者提供了群友的开源实现 `workbuddy-proxy`（纯 Python，2214 行，MIT，
`D:\zhangkun\Downloads\workbuddy-proxy`）。**只做静态代码审读，未运行**。
这份实现把 §7 静态侦察答不了的问题全答了：

### 8.1 §7 两处误判的修正

| §7 当时结论 | 实际情况（由该工具实现证实） |
|---|---|
| 中转面「协议未知、价值大幅缩水」 | **中转面就是 OpenAI 兼容**：`POST https://www.workbuddy.cn/v2/chat/completions`（备选 copilot.tencent.com / wb.tencentbuddy.com），仅支持流式，非流式由代理本地聚合 |
| 「客户端只持有中转会话凭据且被加密，静态提取无望」 | 客户端**确实持有** Keycloak JWT（accessToken + refreshToken），只是静态存储加密（keyblob 信封）、**明文只存在于进程内存**——正确工具是 Windows 内存扫描，不是抓包也不是逆向解包 |

侦察方法论教训：本机有两套 WorkBuddy 变体（`WorkBuddy` 与 `WorkBuddyAI`），
家目录分别是 `~/.workbuddy` 与 `~/.workbuddy-ai`。我只扫了后者——
**模型目录+兑换率的明文缓存（`~/.workbuddy/cache/acc-product-config-v3-*.json`）**
就在漏掉的那一半里。多变体应用的静态侦察必须先枚举全部家目录。

### 8.2 实现机制四件套（照抄即用的协议文档）

1. **鉴权头复刻**（`gateway.py:build_headers`，缺一不可）：
   `Authorization: Bearer <accessToken>` + `X-User-Id` + `X-Refresh-Token` +
   `X-Enterprise-Id/X-Tenant-Id`（企业）+ 客户端伪装
   （`X-IDE-Type/Name=WorkBuddy`、`X-IDE-Version=5.9.3`、`X-Product=SaaS`、
   `x-codebuddy-request: 1`、`X-Agent-Intent: craft`、`X-Private-Data: true`、
   `User-Agent: WorkBuddy/5.9.3`）+ 全套 trace 头（traceparent/b3）。
2. **令牌获取**（`capture.py`）：Windows 进程内存扫描——`VirtualQueryEx` +
   `ReadProcessMemory` 遍历私有/映射内存区，正则提取
   `accessToken`/`refreshToken`/`Bearer `/JWT 形态候选（ASCII + UTF-16LE
   双形态），逐个调 `/console/accounts` + `/v3/config` 验证，命中即存
   `wb-token.json`。备选：浏览器 F12 手动粘贴（跨平台通用）。
3. **积分与目录**：积分 `POST /billing/meter/get-user-resource-summary`
   （个人）/ `get-enterprise-user-usage` + `X-Enterprise-Id`（企业），
   事后结算有延迟；模型目录 `/v3/config`（按账号档位过滤）与桌面缓存合并，
   兑换率 `models[].credits`（如 glm-5.3 x0.69、hy3 系列 x0.00 免费）、
   夜间折扣 23:00–08:00 解析自 `modelPromotions`。
4. **网关容错**：网络层错误才切换端点（4xx 原样透传），token 每请求热读取。

### 8.3 安全审查（运行前必读，已通过）

- 网络目的地仅 3 个官方端点（workbuddy.cn / copilot.tencent.com /
  wb.tencentbuddy.com）+ 127.0.0.1，**无第三方外传面**；
- 无 eval/exec/subprocess/pickle 等危险调用；
- 默认绑定 127.0.0.1，本地 API Key 首次自动生成（`wb-` + 24 hex）；
- `wb-token.json` 是**明文 JWT 落盘**——工具自身设计如此，测试期可接受，
  但这份文件要按密钥对待（不提交、不外传；与我们 `.env` 红线同级别）。

### 8.4 接入方案（结论第三次反转：可行，且便宜）

**方案 A（推荐起步）：借代理，网关加一行。**
群友工具以 `--serve` 模式跑本机（纯标准库，无 GUI 依赖），ZK-AI 在
providers.yaml 加一个普通 OpenAI 兼容供应商指向 `http://127.0.0.1:8787/v1`。
零逆向工作、零新代码，现有机制（限流分桶/自动隔离/墙钟预算/计量）原样生效。
代价：多一个本机进程 + token 失效需手动重抓（工具无自动刷新，401 后重跑
`--capture` 或浏览器重新粘贴）。

**方案 B（验证有量之后）：原生适配器。** 照 §8.2 的头复刻实现
`workbuddy` provider 适配器（流式直传），去掉中间进程。
内存扫描抓取**不进我们代码库**——token 获取走手动粘贴，按脆弱凭据纪律管理。

**脆弱凭据纪律（§5）全部适用**：不进 zk-auto/zk-long 主链、标注提取日期、
用量必须进 cli_usage 账本。已知风险：JWT 过期周期未知（Keycloak 默认
数分钟到数小时不等）、接口形态来自客户端逆向「官方升级可能失效」
（工具 README 自己承认）、积分按账号服务端计量（撞限额是黑盒，
商汤 2026-10-24 整池瘫痪的教训在此同样适用）。

### 8.5 账本收益（模型目录实测，本机账号）

65 个模型带兑换率：`hy3` 系列 **x0.00（免费）**、`glm-5.3-flash` x0.08、
`minimax-m2.5` x0.18、`glm-5.3` x0.69、夜间折扣另计。对一个已付费/体验账号，
这是额度账本上实打实的新行。

### 8.6 ✅ 落地记录（2026-11-09，方案 A 已完成并端到端验证）

**接入形态**：`workbuddy` 供应商（`type: openai_compatible`，base_url
`http://127.0.0.1:8787/v1`）+ 模型 `wb-hy3`（部署 `wb-hy3-workbuddy`，
192K 上下文 / 64K 输出 / 兑换率 x0.00）。

| 验证项 | 结果 |
|---|---|
| 令牌抓取（内存扫描） | ✅ 45 候选验证命中，userId 落 `wb-token.json` |
| wb-proxy 直连（非流式聚合 / 流式 SSE） | ✅ 均通，`usage` 含 reasoning_tokens 细分 |
| 经网关非流式 | ✅ 返回 `provider: workbuddy / deployment: wb-hy3-workbuddy / credential: workbuddy-01` |
| 经网关流式 | ✅ SSE 正常；chunk 的 `model` 保留上游名 `hy3`（已知小差异，客户端以请求值回填） |
| 请求记账 | ✅ `zkadmin/requests` 可见 success/error 与延迟 |
| 失效模式（强杀代理） | ✅ **4.6s 快速 502**（connection_error），不挂死；恢复后无隔离残留 |
| 配置体检 | ✅ `check_config.py` 0 错 0 警 |
| 门禁 | ✅ ruff / mypy / pytest 1288 全过 |

**运行位置**：`exports/_wbproxy/`（gitignore，含 `wb-token.json` 明文 JWT 与
`ui-config.json` 本地 Key——按密钥对待，勿提交/外传）。
**踩到的工具 bug**：`--serve` 模式下自动生成的 `localApiKey` 只存内存不落盘
（GUI 模式才写 `ui-config.json`），进程一重启 Key 就换、外部永久认证失败。
绕过方式：预置 `ui-config.json`（`localApiKey` 自生成）后再启动，server 启动时优先读它。

**运维动作（token 过期时）**：
1. 确认 WorkBuddy 桌面版已登录并运行；
2. `uv run python exports/_wbproxy/main.py --capture`（重扫内存）；
