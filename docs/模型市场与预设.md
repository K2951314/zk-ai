## 模型市场的规矩：加模型前先核对官方文档（2026-11-04）

**用户当场纠正过一次**：加 `sensenova-6.8-flash` 时预设表里没有它，
`preset_for()` 静默回落 `guess_from_name()` 猜了 256K，而官方文档写 1M。
三处一起错才酿成这个事故——以后加任何模型，按下面三步走：

1. **先去官方文档核对，再落预设**。`app/models/presets.py` 的 `_PRESETS`
   是"添加模型"表单的唯一数据源；没有预设就等于让用户对着一张猜测表签字。
   每个数字都要在注释里写清出处（哪份文档、哪一天核对的）。
2. **供应商的 `/v1/models` 不是官方文档**。商汤目录给
   `sensenova-6.8-flash` 报 `context_length: 262144`，**是过期值**——
   实测塞 1,047,678 prompt tokens 正常返回，1,049,xxx 才 400。
   已改规则（`app/api/admin/providers.py`）：目录与文档都有时**取大的**
   （低估窗口不报错，只会让长请求在网关这层被 `context_fits` 判死、
   静默降级到烂渠道——那是必须避免的方向），并在市场行上挂
   `context_window_conflict` → 控制台显示「⚠ 目录与文档不一致」。
   回归测试 2 条在 `tests/test_config_write_through.py`（陈旧小值不能缩小、
   更大的目录值仍要赢）。
3. **规格里凡有"不能"的，要实测验证它真的不能**。见下条。

### sensenova-6.8-flash 的三个坑（都已实测、已写进预设）

| 项 | 官方说的 | 实测 |
|---|---|---|
| 上下文 | 1M | ✅ 1,047,678 通过，1,049,xxx 400 |
| max_tokens | 默认 64K、上限 128K | ✅ >131072 报 `should be in [1, 131072]` |
| 关思考 | `thinking.type` 只支持 enabled | **传 none / disabled 都不报错**，`reasoning_tokens=0`，**但思考搬进 `content`**（开头 `Here's a thinking process:` / `France's capital is Paris.</think>Paris`） |

- ⚠ **思考 token 与正文共享 `max_tokens`**：`max_tokens=1024/2048` + `high` 时思考吃光
  配额，`finish_reason=length`、`content` 为空——客户端拿到 HTTP 200 与零字节。
  8192 起正常。部署里 `max_output_tokens` 给足（现配 65536），别按"回复要多长"写。
  回归点是 `tests/test_presets.py::test_sensenova_68_flash_does_not_advertise_an_off_switch_it_lacks`。
- 它**啰嗦**：`max` 档写 350 字的答案会写到 1800+ 字；要严格字数限制的任务用 `low`。
- **没进任何别名链**（故意的）：中位耗时 28.3s vs `deepseek-flash` 3.8s，进链首会把
  每个请求拖慢 8 倍同一个量级，放链尾又轮不到。定位同 `glm-5.3`——**点名用**。
  数据见 `docs/模型对测-6.8Flash-vs-DeepSeekFlash-20261104.md`。
- `deepseek-flash` 在 8 把 Key × 3 rpm 下仍频繁 `EndpointRPMExceeded`/`EndpointTPMExceeded`
  ——**它的有效可用容量明显比同池的其他模型低**。压测它要么加 Key，要么放慢。

## 同一模型在不同供应商是不同 id：family 对不上就整行变 256K 猜测（2026-11-11）

运营者在华为云 MaaS（provider `HW`）开通了 `deepseek-v4.1-flash-1017`，
市场却显示**上下文 256K、无思考档位**——而官方明写 1M。根因不是规格错，
是**预设表的 family 键与华为目录的 id 对不上**：

- 预设里 V4.1 Flash 的 family 是 `deepseek-flash`（**商汤公告的 id**，
  2026-09-29 那次「产品名↔ID 映射」缺口的补丁）；
- 华为目录用的是 `deepseek-v4.1-flash` / `deepseek-v4.1-flash-1017`，
  既不完全相等、也不被「最长后缀」命中（`endswith`/`startswith` 都不沾）；
- 于是 `preset_for()` 静默回落 `guess_from_name()`——**保守 256K、档位为空**，
  行上只标「预估」，不细看就发现不了。

**这与 2026-09-29「deepseek-v4.1-flash 403」是同一个病根的两次发作**：
预设按供应商 id 收录，新供应商接入时整条流水线（预设/价格/已收录判定）
对它都是瞎子。修复 = 按 HW 补全目录 id 的预设条目（官方 Model List +
计费说明 + Anthropic 兼容接口文档 + 下线公告，全部 2026-11-11 核对，
价格 ¥ 按 7.1 折美元），回归测试钉住「HW 目录 9 个 id 全部命中官方预设」。

顺带三条华为特例（都实测过）：

| 现象 | 结论 |
|---|---|
| 目录里 ArkTS-SPARK 的 id 是 `glm.5.2-arkts-spark`（**带点**） | 官方文档写连字符，但连字符实测 404「Invalid model」、带点 403「未开通」——**以目录 id 建 family** |
| `reasoning_effort=medium` 返回 200 | 官方文档该模型词表是 none/low/high/max；medium 被上游按官方映射（low/medium→high）收下。非法值 400 `ModelArts.81001` |
| 2026-11 下线潮（贵阳一） | kimi-k2.6 已于 11-08 下线（所以它 404）；glm-5.1 于 11-16 下线；V4.1-Flash 非 1017 版 / V4-Flash / openPangu 全系 11-30 下线。**下线模型的 display_name 带「下线」标**（沿用 v4-pro 先例），别加进链路 |

**可复用的规矩**：接入任何新供应商，先把它的 `/models` 目录整个拉下来，

"estimated"` 或 `reasoning_efforts` 为空的，就是没收录——按官方文档补，
别让运营者对猜测签字。

## 两个模型怎么选（2026-11-05 实测）

`sensenova-6.8-flash` 与 `deepseek-flash` 综合分打平（各 8/9），**失败模式不同**：

## 外部 CLI 执行体的模型清单：只有实测算数（2026-11-11）

**改了两次、两次都错，最后靠"真发一次请求"定案。** 教训不是"哪个源对"，
而是**任何清单都不能当权限用**。

### 三方实测对照（同一天、同一个账号）

| 来源 | 数量 | 实测真相 |
|---|---|---|
| `codebuddy --help` 的 `Currently supported:` | 26 | **静态帮助文字**，17 个名字根本不存在（`kimi-k3` / `gpt-6-*` / `grok-4.7` / `hy4-preview` / `primary-model` …） |
| 桌面缓存 `acc-product-config-v3-*.json` | 65 | **整条产品线的模型表**，不是账号权限。混着补全 `codewise-completions`、视频 `kling-video-v3`、图片 `hunyuan-image-alpha-edit`。实测只有 **35 个是对话模型**，26 个 400，4 个不是对话 |
| wb-proxy `/v1/models` | 14 | **也不准**：8 个调不通（`11102 model not found`），而能用的 `hy4free` / `glm-5.3` 它**没列出来** |

> 运营者原话：「workbuddy 模型还是不对，不是试试获取的吗？」
> —— 第一次错在抄帮助文档，第二次错在把桌面缓存当权威。两次都是
> **把某种清单当成了权限**。

### 现行的判据（`app/services/agent/cli/models.py`）

`probe_models()` 对每个候选**真发一次** `POST /v1/chat/completions`：

- 返回 200 且 **产出了内容** → 可用
  - `content` 有字（普通模型）
  - **或** `reasoning_content` 有字（推理模型，正文可能还没开始）
- `finish_reason == "error"` → **硬否决**（`codewise-*` 返回的是
  `` ```\n\n``` `` 这种非空壳子，看"有没有字"判不出来）
- 其它非 200 → 不可用，把上游错误码留在 `error` 里给运营者看

桌面缓存现在**只干一件事**：给实测通过的模型补元数据
（`credits` 兑换率 / `supportsToolCall` / `supportsImages` / `maxInputTokens`），
同时作为**候选 id 来源**（客户端运行时会自动刷新，是本机最新的目录）。

### 为什么界面上还是不对：结论没活过一次重启（2026-11-11 补）

运营者第二次反馈「模型市场里 workbuddy 和执行体里的模型都不太对」时，
代码其实**已经会真发请求了**，但两个界面的默认数据源都不是实测结果：

| 界面 | 之前的数据源 | 现在的默认数据源 |
|---|---|---|
| 模型市场 · workbuddy | wb-proxy `/v1/models` 的 14 个旧 id（`hy4free` / `glm-5.3-flash` 一个没列） | 同一份目录 **∪ 已落盘的实测可用清单**；目录外补进来的行标「实测可用」 |
| 执行体与价格 / `/executors` | `cli_tools.yaml` 里 9 个手工快照，全标「配置快照（未实测）」 | **已验证清单**（`probed=True`），来源徽标「实测可用」 |

根子是 `probe_models()` 的结论只存在进程内存、TTL 10 分钟，网关一重启就丢。
现在结论**合并式落盘**到 `data/model-probe.json`（gitignore，24 小时有效），
`cached_models()` / `cached_model_details()` 在进程缓存冷时读它，
所以「刷新实测」按一次，之后跨重启都生效。

**「最新」怎么处理**：把候选 id 算一个 `candidate_fingerprint` 写进快照；
指纹变了 → `verified_snapshot()["stale"]=True`，模型市场顶部提示
「候选集已变化，到执行体页点刷新实测」。**不偷偷自动发几十个真实请求**——
wb-proxy 后面是真实订阅账号，探测本身就是一次限流压力。
候选集不拿 wb-proxy `/v1/models` 做增量源：2026-11-11 实测它 14 个全是桌面缓存的
子集、反而漏了新模型。参考实现 `workbuddy-proxy` 的 `catalog.refresh()`
（在线 `/v3/config` → 桌面缓存 → 内置兜底）同样说明「目录按账号档位过滤，
不等于你能调它」；本项目不引入它的 JWT，避免把凭据面扩进网关。

### 上下文窗口：真实值优先于预设表（2026-11-11 复查后修）

运营者质疑「hy4 明明就是 1M 左右的上下文，而模型市场里 workbuddy 显示才 200k」
——**属实，是上一轮补行时只塞了 `{"id": mid}`，把桌面缓存的
`maxInputTokens` 丢了**，于是 `model_facts()` 读不到事实、
`context_window_source=preset`，全部落到预设表的 256000。

现在三处一起改：

- `app/models/discovery.py` 的 `_CONTEXT_KEYS` 认 `x_max_input_tokens`
  （wb-proxy 目录自带）与 `maxInputTokens`（桌面缓存），`_VISION_KEYS` /
  `_REASON_KEYS` 认 `supportsImages` / `supportsReasoning`；
- `merge_probed_models()` 补进来的行带桌面元数据，走和目录行完全相同的
  预设 / 价格 / 已收录流水线；
- `provider_models()` 既有规则「探测值与预设值取大」**不动**：实测 960000
  ≥ 预设 256000 → 显示 960000，来源标 `provider`。

真实对照（2026-11-11 桌面缓存）：`hy4free` 960000、`hy3` 192000、
`glm-5.3-flash` / `deepseek-v4-flash` / `minimax-m3.1-flash` 1000000。
⚠ 像 `hy3` 这种「实测值 < 预设值」的会保留预设并带
`context_window_conflict`——那是**刻意**的（宁可上游 400 让运营者看见，
也别在本地悄悄掐掉），不是又一次算错。

### 一次超时不等于模型下线

14:23:19 的一次全量重测里 `kimi-k2.8-preview` 回了 `ReadTimeout`，清单就从
36 变 35——「应用里看到的模型又有差异」有一半是这个抖动。现在
`_write_snapshot()` 合并时区分：

| 本次结果 | 处理 |
|---|---|
| `ReadTimeout` / 连接类异常 / **HTTP 429（限流 / 免费额度用尽）** / HTTP 5xx | **本次没测成**，保留之前真发请求验证过的结论 |
| 其它 4xx（11102 无权限、11103 无后端）/`finish_reason=error`/无产出 | **明确否决**，照常覆盖 |

⚠ 429 是 2026-11-11 现抓的：一次 65 模型全量探测把 `hy4free` 的每日免费额度
打满（错误写明「明日 10:20 重置」），旧逻辑把限流当否决，模型直接从市场消失
——「越探测越掉模型」。现在保留结论的同时把状态放进 `transient`，
模型市场顶部会写「当前限流 / 暂时没调通（仍按实测可用列出）：hy4free」。
**限流是配额状态，不是模型没权限**；被误踢的那次结论已按上一轮实测证据恢复。

探测后还会把落盘快照回填进程缓存，避免内存 10 分钟与磁盘 24 小时两套口径打架。
前端「可调用」列对 `probed` 行直接显示「✅ 实测可用」，不再显示「未验证」；
模型市场表格是 `55vh` 滚动容器，**没有截断**，计数栏会写清
「N 个 · M 实测可用 · K 已收录（表格可滚动）」。

### 「刷新实测」这个动作本身也不能制造抖动（2026-11-11 复查后修）

前一条只保证**磁盘结论**不被瞬时失败冲掉，复查发现接口链路还有两处会抖：

1. `/model-inventory?refresh=true` 是「先 `discover_models()`，再探测」。
   旧代码里 `discover_models()` 把桌面缓存**整份 65 个**写进 `_CACHE`，
   `cached_models()` 又优先读 `_CACHE`——于是刷新一次，运营者看到的从
   「36 个实测可用」退回「65 个候选」（含视频/补全模型），**越刷新越不对**。
   现在 WorkBuddy / CodeBuddy 分支只认「进程实测缓存 → 落盘快照」，
   没有实测结论就返回空；`_CACHE` 只是其它执行体的 live 兜底。
2. `probe_models()` 原来返回**本次原始结果**。`_write_snapshot()` 虽然合并
   保留了历史结论，但 `discover_model_details()` 拿到的还是失败结果，
   于是磁盘没抖、接口第一次响应仍把模型标 ``probed=False``。现在返回
   **合并后的结论**，瞬时失败的模型保留可用，并把 ``probe_error``
   写成 ``暂态：ReadTimeout`` / ``暂态：HTTP 429 …``，前端照常标「实测可用」。

三条回归测试钉住这三条路径（`tests/test_cli_model_catalog.py`）：
刷新后不回到桌面目录、瞬时失败返回合并结论、无实测结论不返回桌面目录。

### 两个探测坑（测试钉住了，别改回去）

1. **`max_tokens=1` 会误杀所有推理模型**。推理模型把 token 全花在
   `reasoning_content` 上，`content` 为空、`finish_reason=length`。
   实测误杀 **16/39**（`hy3` / `hy4free` / `step-5-preview` …），
   比不探测还糟。现在用 `_PROBE_MAX_TOKENS = 200`。
   ⚠ 2026-11-11 晚间发现**控制台「模型市场 → 验证可调用」那条路还是
   `max_tokens=1`**（同一个坑修了执行体漏了市场，历史上「修市场漏健康检查」
   的同型事故）——已对齐成 `_VERIFY_MAX_TOKENS = 200`，回归测试
   `test_verify_probe_gives_a_real_token_budget` 钉住。
2. **`codewise-*` 是有内容的空壳**。它们返回 `` ```\n\n``` ``，
   只看「content 非空」会把补全模型放过。现在 `finish_reason=error`
   是硬否决。

### 结果（2026-11-11 真机）

`GET /zkadmin/agent/executors/cli-grinder/models` → `source: probed`，
**35 个可用 / 65 个候选**，每个不可用的带错误摘要。
免费档（×0.00）：`hy4free`（960K ctx）、`hy4flash-exp1..4`、`hy3`/`hy3-b`/`hy3-c`。

### 一条附带修掉的 bug

**四个独立页都不认 `?token=`**（只有 `console.js` 认）。`deploy-server/README.md`
教运营者用 `/ui/?token=<TOKEN>` 直登，但飞书卡片深链到 `/ui/models?token=…`
时页面显示「管理令牌缺失或无效」——URL 里明明带着令牌。

已在 `common.js` 的 IIFE 顶部修：读 `?token=` → 存 localStorage →
`history.replaceState` 抹掉 query。用 `replaceState` 不用 `pushState`：
令牌不该留在浏览器历史里。

`test_common_js_only_keeps_token_in_localstorage` 原来直接禁掉
`location.search`，把「读一次然后抹掉」这个正确做法也拦了。**改成按意图断言**：
只写 localStorage；如果读了 URL 就必须 `replaceState` + `delete("token")`。
