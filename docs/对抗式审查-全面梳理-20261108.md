# 对抗式审查 · 全面梳理（2026-11-08）

第五轮对抗式审查。与前三轮（2026-09-29）和手填模型轮（2026-11-07）不同，这次是
**全库梳理 + 方向判断**：后端核心、Agent/事件子系统、前端三条线并行深审，
所有 P0/P1 发现均由主会话亲自复核过源码，不是子代理的一面之词。

审查时的代码状态：工作区有 15 个文件、+815 行未提交改动（任务台/Agent 方向），
本报告基于该状态。门禁实测：**ruff ✅ mypy ✅ pytest 全量 ✅**。

---

## 0. 第一性原理：这个东西到底是什么

剥掉所有实现，这个项目是**一个人的 AI 运行时**：用最小成本、最少注意力，
把一堆廉价/免费上游拼成可靠生产力。三层资产，质量严重不均衡：

| 层 | 内容 | 成熟度 | 判断 |
|---|---|---|---|
| L1 模型调度 | 路由/凭据池/限流账本/部署隔离/缓存粘性 | 9/10 | **过度打磨**。隔离阶梯、墙钟预算、粘性亲和的精度是给多租户生产网关设计的，实际用户 1 人，边际收益已递减 |
| L2 执行 | Agent 任务台 + CLI 执行体 + 任务空间 | 6/10 | 七成完成（总控大脑文档自评），cancel 不 kill、并发闸绕过、成本恒 0 |
| L3 事件 | 事件中台 + 飞书推送 + 审批闭环 | 4/10 | 闭环的**形状**有了，但痛觉传导是断的（见 §2.2） |

**核心洞察 1：瓶颈已不在模型层，在「注意力回路」。** 本轮 P1 级发现里 5 条是同一个病：
系统干了活/出了事/要拍板，但人不知道（静默窗口吞审批推送、failed 判死不推送、
ask 内容不进卡片、open 口径漏 waiting_decision、agent SSE 断线无恢复）。
这不是五个 bug，是一个缺失的子系统：**通知可靠性层**。

**核心洞察 2：成本是所有决策的输入，现在恒为 0。** `budget_cny` 死字段、
worker 交活不带成本、`cli_usage` 表不存在。动态选执行体（自定 P0）、预算熔断、
手机看板，全都以成本真值为前置。文档自己写对了一半：「先接成本，再谈熔断」。

**核心洞察 3：手机远控不是新功能，是注意力回路的移动端变现。** 服务端地基
（审批 API、事件流、飞书卡、`?session=` 深链）全部就绪，缺的是最后一公里
（见 §7）。一个人 + 一台服务器 + 一部手机 = 一家 AI 公司的完整控制面——
这是这个项目区别于 litellm/openrouter 红海网关的定位。

## 1. P0 — 必须马上修（安全）

### 1.1 消耗器日志端点完全无鉴权，且不受 admin 开关控制 ⛔

- 位置：`app/api/burner_log.py:33`（router 无 `dependencies=[Depends(require_admin)]`）、
  `app/main.py:130`（在 `if settings.admin_enabled` 之外无条件挂载）
- **主会话已亲自复核属实**。对照 `app/api/agent.py:35`、`app/api/events.py:41-43`
  都有 router 级鉴权，唯独这里没有。
- 后果：①`GET /zkadmin/burner/log/tail` 匿名回服务器日志全文（账号名、积分、错误细节）；
  ②`/stream` 是匿名无限 SSE 流（每秒轮询永不退出），现成的慢速 DoS 面；
  ③`admin_enabled=false` 时其它 admin 面 404，这两个端点**仍然活着**——
  `main.py:137-140` 的注释声称「必须与 admin 同一个开关」，代码没落实。
- 根因：SSE 的 `EventSource` 不能带自定义 header，当年为了让它能连就把鉴权整个去掉。
  但降级轮询路径（console.js:3053）明明带了 `X-Admin-Token`，tail 端点完全可以 header 鉴权。
- 修法：router 挂 `require_admin`；SSE 用 `?token=` query 参数（常数时间比较）或
  一次性短码。**这是手机远控的前置条件**——远控会把暴露面从本机扩大到手机网络。

### 1.2 admin 面默认裸奔 + 一个端点明文下发推理令牌

- 位置：`app/api/deps.py:44-46`（`if not expected: return`——未配置 `ZKAI_ADMIN_TOKEN`
  时整个 `/zkadmin/*` 开放）；`app/api/admin/chatgpt.py:149`（`"api_token": gateway_token or ""`
  ——响应体直接携带 `ZKAI_API_TOKEN` 真值）
- **已亲自复核属实**。`admin_enabled` 默认 `true`、`admin_token` 默认 `None`
  （settings.py:152-153），即**默认状态就是裸奔**。启动时只有一条 warning。
- 攻击链：`ZKAI_HOST=0.0.0.0` + 忘配 token → LAN 内任何机器匿名 `GET /zkadmin/chatgpt`
  → 拿走推理令牌 → 白嫖 `/v1/*`。
- 修法：fail-safe——监听非回环地址且未配 admin_token 时**拒绝启动 admin 面**
  （比现在的 warning 强一档）；`api_token` 真值改为按需单独端点 + 显式确认。

### 1.3 配套两处（同一批修）

- `/v1/models` 无鉴权（`app/api/models.py:9`）：聊天面全部要 Bearer，模型清单
  （含别名、targets、上下文窗口）却匿名可读。补 `require_client_auth`。
- `/health` 无鉴权泄露内部信息（`app/api/health.py:44-48`）：监听地址、绝对路径
  （burner_log_path/config_dir/data_dir）、全部渠道健康状况。公网部署时这是部署地图。
  至少把路径类字段收敛掉。

## 2. P1 — 一周内

### 2.1 任务空间端点路径穿越

- 位置：`app/api/agent.py:262-268`（detail）、`271-278`（release）。
  紧挨着的 `_task_space_path()`（252-258）有 `is_inside` 越界校验，这两个端点没用它。
- `task_id` 来自 URL：`..%2F..%2Ftarget` 可读任意 `state.json`、删任意 `state.lock`。
  在 admin 鉴权之后，所以定 P1 不定 P0。修法一行：复用 `_task_space_path` 或
  `task_id` 白名单 `^[\w\-]+$`。

### 2.2 静默窗口永久吞掉「等你拍板」，无补发（已亲自复核）

- 位置：`app/services/events/notify.py:99-103`。静默检查对**所有** tell 等级生效
  （包括 `always`，docstring 说的豁免条件是「规则没配静默」而不是「always 豁免」）。
- 事件默认 `silent: ["23:00-08:00"]`：23:30 产生的 `need_decision` 推送被吃掉 →
  状态终态 `waiting_decision` → 不在 `reclaim_stale` 范围、不在 `stats.open`
  （`event.py:32` OPEN_STATES 只含 received/running）→ **除非人主动打开 /ui/events，永远沉底**。
- 同病：worker 第 3 次判死进 `failed` 只 `logger.error`（`service.py:250-252`），
  不推送——最需要人看的失败反而只有日志。
- 修法：①`waiting_decision`/`failed` 进补推队列，静默结束补推；②`need_decision`
  可配置豁免静默（半夜吵不吵醒运营者，给开关让运营者拍板）；③open 口径纳入 waiting_decision。

### 2.3 回执的 ask 内容进不了飞书卡片

- worker 侧指令要求把要人拍板的问题写进 ```` ```zkai ```` 回执块的 `ask` 字段，
  但解析后 `ask/notice/resolve` 只落库（`service.py` 回执处理），`build_card`
  （notify.py:116-124）只渲染 verdict 正文。Agent 按提示词认真写了 ask，人在飞书上看不到。
  事件中台文档 §10 自己标了这条 P2，本轮确认它直接削弱审批闭环。

### 2.4 「停止」是安慰剂：cancel 不 kill 子进程

- 位置：`app/services/agent/service.py:658-669`（只设标志位 + deny_all）；
  `service.py:430-433` 注释自认 run_delegation 不支持中途 kill；runner.py:187-190
  超时 kill 只杀直接子进程（npm shim→node→CLI 孙进程存活），kill 后不 wait。
- 后果：点了停止，外部 CLI 照常烧免费额度（最长 1800s），任务空间租约到 finally 才释放。
  总控大脑文档把真 cancel 排在 R4，但前端既然给了一颗「停止」按钮，就不该是假的。

### 2.5 `?token=` 把管理令牌写进浏览器历史与反代日志

- 位置：`console.js:2690-2702`。`replaceState` 只抹地址栏，抹不掉历史记录和访问日志。
- 这是给手机留的方便门，方向对、机制错。手机远控必须换一次性交换码（见 §7.3）。

### 2.6 直跑委派绕过全部并发闸 + followup TOCTOU

- `service.py:322-324、367-369、545-547`：`@` 点名直跑 `create_task` 不进 `_sem`
  （agent_max_concurrent=3 只限模型循环），一口气可起 N 个 1800s 子进程。
- `service.py:223-243`：followup 的状态检查与注册 `_running` 之间无原子性，
  并发 followup 可双开 loop 交替写库。单人使用概率低，但排障极难。

## 7. 手机远控设计（推荐路线的落点）

### 7.1 形态决策

**两条腿：手机浏览器开控制台 + 飞书卡片推送。** 不做原生 App、不做 PWA 离线、
不做小程序。理由：审批/看状态是低频操作，浏览器够用；零依赖约定不破；
飞书 webhook 已通。拓扑：手机 → 公网服务器上的网关（public_base_url 已有）；
本机 NAT 后那台不直接暴露（要远控走 tailscale 点对点，运营者可选）。

### 7.2 前置条件（不做完不准上线远控）

§1 的 P0 全部修完。远控把暴露面从本机扩大到公网+手机，安全债会直接变事故。

### 7.3 令牌交接（核心技术决策）

现状 `?token=` 进 localStorage 有泄漏面（§2.5）。改成**一次性交换码**：

1. 飞书卡片 URL 带 `?code=<一次性短码>`（60s 有效、用后即焚，服务端存哈希）；
2. 页面加载发现有 code：`POST /zkadmin/auth/exchange` 换真令牌；
3. 真令牌只存 sessionStorage（关标签即失效）或内存；
4. URL/历史/反代日志里只有短码，泄漏窗口 60s 且单次有效。

M2 可再加登录失败限速。**不做的**：Cookie 长会话（CSRF 面）、自建应用卡片回调
（第二阶段再说）、JWT（一个人用不上无状态令牌）。

### 7.4 分期

**M1「看 + 批 + 追」闭环（预计 2-3 天）**——这是全部建议里性价比最高的一件事：

1. `common.js` 共享外壳（esc/api/toast/令牌管理/登录框/导航），五页收编，
   顺手删 ~500 行重复；
2. events.html 卡片化 + 登录兜底；
3. agent.html 手机布局补齐（100dvh、顶栏 wrap、safe-area、44px 触控、16px 输入）；
4. agent SSE 退避重连 + `waiting_approval` 轮询兜底（搬 console.js:3018-3066 现成代码）；
5. 飞书卡片深链：`/ui/agent?session=xx`（前端已支持，notify.py:158 拼 URL 即可）、
   事件卡带事件 id；
6. §2.2 的静默补推 + ask 进卡片（和远控是一件事的两半：推得出去，点得进来）。

M1 完成后的体验：手机上收到飞书卡 → 点开直达对应会话/事件 → 看到要拍板的问题原文 →
批准/否决 → 看进度滚动。**「半夜被吵醒 30 秒解决战斗」而不是「第二天上班发现 Agent 昨晚就停了」。**

**M2「管」（可选）**：关键操作远控（部署启停、消耗器开关、重启确认）；
need_decision 豁免静默的开关；`waiting_decision` 纳入 open 口径后的待办角标。

**M3「看板」（依赖成本账本）**：手机看板加成本/额度/成功率卡片。

### 7.5 明确不做

- 拆构建化前端框架（违背零依赖约定，收益低）；
- PostgreSQL/Alembic（单机单人用不上）；
- 多租户化（没有第二个用户）；
- 通用网关红海（litellm 已经赢了，别去挤）。

## 8. 方向判断与路线排序

### 推荐：注意力回路优先，成本账本紧随，调度层冻结新功能

| 序 | 事项 | 量 | 理由 |
|---|---|---|---|
| 1 | §1 P0 安全四连（burner_log/admin fail-safe/models/health） | 半天 | 一切的前置，远控前必须 |
| 2 | 通知可靠性层（§2.2+§2.3：补推+ask 进卡片+open 口径） | 1 天 | 五个 P1 是同一个病；这是系统「痛觉」 |
| 3 | 手机远控 M1（§7.4） | 2-3 天 | 把已有能力送到碎片时间，注意力杠杆最大 |
| 4 | `cli_usage` 成本账本（总控大脑 R2） | 2-3 天 | 动态选执行体/熔断/看板共同的输入，一石三鸟 |
| 5 | 总控大脑 R3-R4：动态选执行体、worktree 隔离、真 cancel | 按原规划 | 此时才有数据支撑打分 |
| 6 | 死代码清扫（§3 工单）+ 桥接表 fail-loud | 半天 | 择机穿插 |
| 7 | Scheduler 合并重构、AgentService 拆分 | 大 | 另立会话，带变异测试；不阻塞上面任何事 |

### 为什么是这个顺序

- 运营者的稀缺资源是**注意力**，不是模型算力。L1 已经比需要的好，
  L3 断在最后一公里。手机远控 + 通知可靠性 = 把「跑着的东西」变成「能托付的东西」。
- 成本账本是当前**最高杠杆的一张表**：没有它，动态选执行体是拍脑袋打分，
  预算熔断是假闸（budget_cny 现状），手机看板没内容。
- 调度层冻结新功能 ≠ 不修 bug：P0/P1 照修，但不再加新机制——隔离阶梯、
  粘性、墙钟预算的打磨精度已经超过单人场景的需要。
