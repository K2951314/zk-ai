# NVIDIA 排查报告：是不是网关配置的问题？

日期：2026-09-29　触发：运营者问「会不会也是你设置的问题导致无法使用，不要着急限制，先排查」

---

## 结论

**不是网关配置的问题。** 是 NVIDIA 账号/组织侧的推理端点未对该账号开通。

**但我确实发现了一个属于我的问题**（见 §3）：健康检查只测「目录可达」不测「推理可用」，
所以把一个 100% 不可用的供应商一直报成绿灯——这才是它长期留在故障转移链上、
累计烧掉 60.9 小时的根本原因。

---

## 1. 排除过程（逐项，全部实测）

| # | 假设 | 测法 | 结果 |
|---|---|---|---|
| 1 | 请求体被网关改坏了 | 打印适配器 `build_payload()` 的实际输出 | `{"model": "z-ai/glm-5.3", "messages": [...], "max_tokens": 8}` — **与裸请求逐字一致** |
| 2 | 模型名写错了 | 对照官方页代码示例 | 官方示例就是 `model="z-ai/glm-5.3"`，**我们的配置是对的** |
| 3 | base_url 写错了 | 对照官方示例 | `https://integrate.api.nvidia.com/v1`，**一致** |
| 4 | 代理干扰 | 同一请求 `trust_env=True` / `False` 各跑 2 次 | **4/4 全超时** → 与代理无关 |
| 5 | 某个 Key 坏了 | 两个 Key（`NVIDIA_API_KEY` / `_02`）各测 2 个模型 | **两个 Key 完全相同地失败**，且 kimi-k3 报**同一个 function id** |
| 6 | 鉴权有问题 | `GET /v1/models`、`GET /v1/models/{id}` | **200 正常**（鉴权没问题） |
| 7 | 只有 glm-5.3 有问题 | 换 5 个不同家族的模型 | **全废**：4 个 `404 Function not found`、1 个挂死 |
| 8 | 是不是我们的调用方式特殊 | **原样复制官方文档的示例代码** | **49.7 秒超时** |

第 8 项是最有力的：**NVIDIA 自己文档里的示例代码，一字不改，同样跑不通。**

### 症状分类

```
z-ai/glm-5.3        → 挂死（121s 仍无响应，不是慢）
moonshotai/kimi-k3  → 404  Function '1586112a-...' version 'null': Specified function not found
google/gemma-2b 等  → 404  Function '...' Not Found
```

`Function ... Not Found` 是 NVIDIA NVCF（云函数）层的错误：**模型在你账号下没有对应的
函数部署**。论坛里有同名帖：
「Request to enable **Public API Endpoints** for my personal organization — 404 Function Not Found」。
官方 `developer.nvidia.com/nim` 也写明：**Developer Program 会员**才能使用
NVIDIA 托管的 NIM API。

**所以要做的是**：去 build.nvidia.com 查该账号/组织的 Public API Endpoints 权限
（以及免费额度是否用尽）。这不是改配置能解决的。

- `providers.yaml`：`nvidia` → `enabled: true`（不预先限制）
- `models.yaml`：`glm-5.3` / `glm-5.3-flash` → `enabled: true`

所以 NVIDIA 现在「启用但不参与路由」——不会给每个请求加 60 秒等待，
但你可以用模型名 `glm-5.3` 直接点名测试。要放回链里说一声。

## 3. 我确实有的问题：健康检查一直假绿

**旧实现**（`app/providers/base.py`）：

```python
async def health_check(self, credential=None):
    models = await self.list_models(credential)   # 就是 GET /v1/models
    return HealthCheckResult(ok=True, models=models)
```

它只证明「**鉴权通过、目录可达**」。NVIDIA 的推理 100% 不可用，而健康检查
**一直报绿灯**——于是它留在所有故障转移链上，60.9 小时的等待就是这么来的。

**这和「模型市场只看目录」是同一个错**：把「目录里有」当成了「能调用」。
同一个会话里我修了市场那一处，却漏了健康检查这一处。

**已修**：`health_check` 在目录通了之后，**再对前 N 个模型各发一次
`max_tokens=1` 的真实推理**；任意一个成功即健康（目录里可能混着无权限条目，
只探一个会误报），全失败则如实报不健康并带上原因。

### 实测对比（四个真实供应商）

| 供应商 | 旧健康检查 | 新健康检查 |
|---|---|---|
| nvidia | ✅ **假绿** | ❌ 目录可达（81 个模型）**但推理全部失败** |
| sensenova | ✅ | ✅ 目录与推理均通过 |
| modelscope | ✅ | ✅ 目录与推理均通过 |
| StepFun | ✅ | ✅（首轮测试脚本取错 Key 字段名，误报一次，已确认） |

新增 4 个测试（`tests/test_adapters.py`），含「目录通但推理全废必须报红」
「目录里混着坏模型时别误杀」「`health_probe_models=0` 回到旧行为」。

## 4. 与上一轮「静默回滚」的关系（更正）

上一轮我把 09:15 那次 `nvidia` 被改回 `enabled: true` 归因成「控制台保存静默回滚」。
**运营者指出那是他有意调回去的**——我把人的操作错怪成了 bug。

机制本身是真的（网关不监听配置文件、控制台表单用内存旧值、保存即写回），
已加的陈旧检测闸仍有价值；但**那次的具体成因是我的归因错误**。
已更正 `AGENTS.md` 与记忆中的表述。
