## 3. 优化后的架构

```
┌─ 信号源（你已有数据，只是没人读）──────────────────────────┐
│ /health 隔离状态 · 429 突增 · config 漂移 · git 落后          │
│ check_config 失败 · 消耗器状态 · GitHub PR/issue            │
└──────────────────────┬──────────────────────────────────┘
                       │ ① 统一事件格式（source / type / object / summary / link）
                       ▼
┌─ 事件中台（新建，约 600 行）──────────────────────────────┐
│ 去重（语义键 + 静默窗口）→ 规则匹配（rules.yaml）→ 建任务     │
│ 沉淀（events 表：谁来的、给了谁、结论、花了多少）             │
└──────────────────────┬──────────────────────────────────┘
                       │ ② 派单：只写「角色 + skill + 指令」
                       ▼
┌─ 本机 worker（长轮询，照抄他的模式）──────────────────────┐
│ 拉任务 → 调 cli-claude / cli-grinder → 回传结论 + 成本       │
│ 你本机在 NAT 后，服务器公网 → 必须由本机主动拉，不能推        │
└──────────────────────┬──────────────────────────────────┘
                       │ ③ 需要拍板时
                       ▼
┌─ 审批出口（复用 agent.html，加推送）──────────────────────┐
│ Windows 通知 / 邮件 / 控制台卡片 → 你点一下 → Agent 继续     │
└─────────────────────────────────────────────────────────┘
```

**关键：不要新建"选模型"这一层。** 卡兹克的 `rules.json` 里 `"to": "m5-claude"` 同时决定了机器和模型，因为他没有网关。你的分层更清楚：

- 事件规则只决定 **`to: 角色`**（`cli-claude` / `cli-grinder`）
- 角色用哪个 CLI、哪个模型、免费还是收费 → 已由 `cli_tools.yaml` 决定
- 模型内部再往下（供应商、Key、失败转移、隔离）→ 已由 `models.yaml` + 路由层决定

**这是你比他那套更耐改的地方**：换模型改 `cli_tools.yaml` 一行，换供应商改 `models.yaml` 一行，都不用动规则。

## 4. 三处不该照抄

### 4.1 不要自建 CI 中台

他自建是因为量大：AIHOT 单项目 10 月合了近 1000 个 PR，一天二三十个，GitHub 会员 3000 分钟根本不够，超额每月 50 美金。

你的量级是**单人项目、一周几个 PR**。GitHub Actions 私有仓库 Free 计划 2000 分钟/月，公开仓库不限量。自建 runner 意味着你要维护虚拟机模板、清理、发布脚本、故障恢复——**这些维护成本远大于省下的那点分钟数**，而且你的服务器还跑着网关，别把 CI 挤上去。

**但"五步闭环"要保留，只是不自己造机器**：

| 步骤 | 文章做法 | 你的做法 |
|---|---|---|
| 审查 | 本地 CI 调 Codex | GitHub Actions 里调你的网关（`/v1/chat/completions`，模型 `zk-auto`）做 diff 审查，只读、只报真错、最多 3 轮 |
| 检查 | 本地虚拟机 | Actions 里的 `ruff` + `mypy` + `pytest`（你门禁本来就全绿，直接搬） |
| 合并 | 本地 CI 调 GitHub | 分支保护规则：审查 job + 检查 job 双绿才可合 |
| 发布 | 专用虚拟机 | 现有的部署方式（git pull + restart），由 Actions 触发 |
| 核实 | 问线上版本 | 拉 `/health` 比对 commit，写回 PR 评论 |

**唯一值得自建的场景**：等你哪天一天十几个 PR 了再说。现在做就是提前优化。

### 4.2 不要做"自动化小镇"可视化

那个渲染视频很爽，但它是**系统跑起来之后**的产物。你现在连事件都没有，做一个空的小镇只会消耗掉你本可以用在 P0 上的注意力。等 events 表里有几百条数据了，一张按流水线分组的成本/成功率看板就够用。

### 4.3 不要自动化"用户反馈"

他明确说了这条**故意不交给 Agent**，而且这是全篇最诚实的一段。你的对应物是：用户直接找你说的问题、GitHub issue 里的真实抱怨。这类东西的**价值恰恰在于你要亲自读一遍**——它给你的是"该做什么"的判断，不是"执行"。让 Agent 去读，等于把方向盘交出去。

**P0 第一条的完整闭环长这样**（这是 MVP 要跑通的那一条）：

```
/health 里 3 个部署被隔离，且都是 sensenova
  → 事件：{source: zkai-gateway, type: health.quarantined, object: "3 deployments"}
  → 规则命中 → 派 cli-claude，cwd=D:/zhangkun/AI/ZK-AI，skill=zkai-ops
  → 指令：「按 skill『隔离排查』一节：查 burner 是否在烧、查 429 分布、给出根因判断。只读，不改配置。」
  → Agent 读完日志/DB，回结论：隔离原因 = tpm 打满（burner 在跑），建议关 burner
  → 这条结论涉及"停服务"→ 推到审批 → 你点一下 → 它去关
  → events 表留下：什么时候、谁触发、结论、花了多少 token
```

跑通这一条，剩下的事件源全是"加一条规则"的事——这就是中台的价值。

## 6. 数据模型与规则格式

### 6.1 新表（只加一张，别铺开）

```sql
CREATE TABLE events (
  id            INTEGER PRIMARY KEY,
  source        TEXT NOT NULL,        -- zkai-gateway / github / server / manual
  type          TEXT NOT NULL,        -- health.quarantined / pr.opened / git.behind
  object        TEXT,                 -- 受影响对象，如 "sensenova-03"、"PR#128"
  summary       TEXT NOT NULL,        -- 一句话，给审批卡片用
  link          TEXT,                 -- 跳回原处
  payload       TEXT,                 -- 原始 JSON，排查用
  dedupe_key    TEXT NOT NULL,        -- 语义键，不是消息 id
  received_at   TIMESTAMP,
  rule          TEXT,                 -- 命中的规则名，没命中为 NULL
  state         TEXT,                 -- received / running / done / failed / dropped / waiting_decision
  role          TEXT,                 -- 派给了哪个执行体
  session_id    TEXT,                 -- 关联 agent_sessions，能直接跳回当时的会话
  verdict       TEXT,                 -- Agent 的结论
  need_decision BOOLEAN DEFAULT 0,
  cost_tokens   INTEGER DEFAULT 0,
  cost_cny      REAL DEFAULT 0,
  attempts      INTEGER DEFAULT 0
);
```

`session_id` 那一列是重点：文章说"点开任何一件任务，还能直接跳到当时 Agent 干活的那个会话"——你已经有 `agent_sessions` + SSE，这一列就实现了。

### 6.2 规则文件（`config/events.yaml`）

用 YAML 不用 JSON，因为你的 `ConfigWatcher` 已经会热加载 `config/*.yaml`——改规则不用重启，这是白捡的。

```yaml
rules:
  - name: 网关健康异常
    when:
      source: zkai-gateway
      types: [health.quarantined, health.degraded, rate_limit.burst]
    to: cli-claude                      # 执行体角色，不是模型名
    cwd: "D:/zhangkun/AI/ZK-AI"
    skill: zkai-ops
    ask: "按 skill『隔离排查』一节处理。只读诊断，不要改任何配置。"
    group: gateway-health               # 去重分组
    dedupe_window: 1800                 # 同组 30 分钟内只开一条
    parallel: 1
    tell: needed                        # always / needed / never
    max_turns: 12
    budget_cny: 2.0

  - name: 服务器代码落后
    when:
      source: server
      types: [git.behind]
    to: cli-claude
    cwd: "D:/zhangkun/AI/ZK-AI"
    skill: zkai-sync
    ask: "列出落后提交与涉及文件，给同步步骤。不要执行 reset。"
    group: server-sync
    dedupe_window: 3600
    parallel: 1
    tell: needed
```

**去重键必须语义化**：`sha256(source + type + object + 状态指纹)`，不能用消息 id。原因见文章那段——网络抖一下来源会重发，同一个人补一句话又是一条。你的健康轮询每 30 秒一次，不去重的话半小时能给你开 60 条任务。

## 7. 决策边界（直接照抄他的清单，落地成配置）

| 必须你批 | 可以 Agent 自己干完 |
|---|---|
| 删数据 / 清表 | 只读诊断、查日志、查 DB |
| 停服 / 重启 / 改 systemd | 跑测试、跑 lint、跑体检脚本 |
| 花钱（调付费模型、买额度） | 开 PR、改自己分支、写报告 |
| 对外发消息（邮件、PR 评论、群消息） | 改本地文档、整理待办 |
| 改产品方向 | 生成差异报告、给方案建议 |
| 新建 / 轮换密钥 | 复现问题、定位到文件行号 |
| 改权限、改分支保护、force push | 归档、清理自己的临时文件 |

**另外两份文件，照抄他的做法，这是整套系统里最被低估的东西**：

1. `docs/卡兹克定的事.md` → 你的版本：`docs/我定的事.md`，只记你亲口做的决定 + 原话 + 日期
2. `docs/定了不做的事.md`，你拒绝过的，Agent 再碰到直接照着回答，不再来烦你

没有这两份，Agent 会在同一个问题上问你第 N 遍——这是"批奏折"体验崩掉的头号原因，比技术问题严重得多。

## 8. 文章没讲、但你必须补的四件事

他那套跑了 1 年，这些坑他一定踩过，只是没写。你现在补上能少踩：

**① 失败兜底**
任务超时 / 执行体进程挂了 / Agent 死循环。要有：单任务超时（`cli_tools.yaml` 里已有 `timeout`）、`attempts` 上限 3 次、轮次上限（`max_turns`）、死信状态（`failed` 而不是无限重试）。

**② 预算熔断（你的独有优势）**
他有订阅额度，只能肉眼看"3 天用掉 90%"。你有 `usage_records` 表，能精确到每次调用。所以规则里直接写 `budget_cny`，按日累计，超了自动降级到免费档执行体（`cli-grinder`）或直接停派。**这是文章做不到的事，别浪费。**

**③ 静默时段**
半夜三点弹一条"有个部署被隔离了"——除非是线上挂了，否则就是纯骚扰。规则里加 `silent: ["23:00-08:00"]`，静默期只落库不推送，早上汇总一条。

**④ 审计**
每条任务留：谁触发、命中的哪条规则、Agent 干了什么（transcript 已有）、花了多少、最后谁批的。出事时这是唯一能复盘的东西。

## 9. 落地路线

| 阶段 | 内容 | 产出 | 估时 |
|---|---|---|---|
| **P0** | `events` 表 + `POST /zkadmin/events` 收事件 + `events.yaml` 规则匹配 + 控制台一个"事件流"列表 | 事件能进来看得见，但还不派单 | 半天 |
| **P1** | `scripts/agent_worker.py` 长轮询 + 调 `cli-claude` + 回传结论 + 语义去重 | **第一条闭环跑通**（网关隔离 → 诊断 → 结论） | 1 天 |
| **P2** | 审批推送（Windows 通知 / 邮件）+ 预算熔断 + 静默时段 | 离开控制台也知道有事 | 1 天 |
| **P3** | 补 3 个事件源（config 漂移 / git 落后 / PR） | 中台开始产生日常价值 | 1 天 |
| **P4** | GitHub Actions 五步闭环 | 代码从提交到上线不需要你 | 1～2 天 |
| **P5** | 数据看板（按流水线看成本 / 成功率 / 平均耗时） | 换模型、改规则有数据依据 | 半天 |

**P1 结束就该停下来观察一周**，别急着往下堆。规则写得再漂亮，跑起来一定会发现"这条根本不该派 Agent"、"这条一天触发 200 次"。让真实数据教你改规则，比一次设计到位靠谱。

## 10. 需要你补充的信息

按阻塞程度排序，前 3 条不定下来我没法开工：

### 🔴 阻塞项

1. **worker 放哪台机器？**
   你的本机在 NAT 后面，服务器是公网。长轮询模式要求"跑 Agent 的机器主动去拉任务"。而 `cli-claude` / `codex` 的登录态在你 Windows 本机上，服务器上没有。
   → 默认方案：**Windows 本机跑 worker，服务器只做中台**。前提是这台机器白天基本开着。
   → 需要确认：这台 Windows 机器是否长期开机？休眠时 worker 会断，任务会积压。

2. **审批从哪弹给你？**
   文章用飞书卡片。你没有飞书（企业微信 connector 当前是关闭状态）。
   候选：① 控制台 `agent.html` 已有卡片 + 本机 Windows 通知 ② 邮件（内置 Agent Mail 可直接用）③ 打开企业微信 connector ④ 全部要。
   → 需要确认：你手机上希望怎么收到"有事要你拍板"？

3. **第一个要自动化的场景，就选网关异常诊断吗？**
   我建议是（理由见 §5）。但如果你现在最痛的是别的（比如服务器同步、PR 审查），换掉，别按我的顺序。

### 🟡 需要确认（不阻塞 P0，但影响设计）

4. **哪些执行体是真有额度的？** `cli_tools.yaml` 里 claude / codex / codebuddy / gemini / qoder 全 enabled，但 enabled ≠ 能用。哪些是你付了钱/有免费额度的？哪些只是配了没验证？—— 决定规则里 `to:` 怎么填。
5. **单日预算上限**多少？超了是降级到免费档还是直接停？
6. **Agent 能不能 push？** 允许 push 到 feature 分支，还是只能本地改完等你合？
7. **静默时段**：几点到几点不推送？
8. **数据保留**：events 表留多久？（建议 90 天，超期归档到文件）
9. **服务器上能不能加常驻服务？** 你有 systemd + polkit 的经验，应该没问题，但确认一下磁盘和内存余量够不够跑中台。

### 🟢 建议你先想清楚（不给答案也行，但会决定系统好不好用）

10. **"我定的事"那份文件，你现在能回忆起几条？** 先写 5 条试试。如果一条都写不出来，说明决策边界还没成形，那时候做自动化会天天被问同一件事。
11. **你能接受 Agent 犯错到什么程度？** 全自动上线 vs 每步都确认，中间有很多档。文章选的是"只在 7 类事情上问你"，这需要你对 Agent 有相当信任。你现在的信任水位在哪？
