# 对抗式审查：模型市场「手填上游模型 ID + 实测」（2026-11-07）

## 目标与第一性原理

要解决的问题：**供应商网页上的模型 ≠ 它的 `/v1/models` 目录**。
2026-11-07 实测 NVIDIA：网页模型库 105 个、API 目录 84 个，`kimi-k3.1-pro`
只在网页。市场只认目录，运营者就永远看不到新模型。

拆到不可再拆的三个断言：

1. 手填的 ID 必须走与目录模型**完全相同**的补全链路（预设 / 牌价 / 已收录），
   否则会出现两套行为，迟早对不上。
2. 手填的模型**必须实测**才能添加——目录里没有它，更不能凭名字相信它。
3. 手填这个动作**不能引入新的失效模式**（脏输入、超长输入、目录失败、竞态）。

## 审查方法

逐条攻击上面的假设，再跑门禁 + 真实网关端到端。不看"我写了什么"，
只看"什么情况下它会错"。

## 发现并修复的问题

| # | 问题 | 后果 | 修复 |
|---|---|---|---|
| 1 | 目录探测失败时函数**早退** | 手填入口在最该用的时候（NVIDIA 目录本身就常超时）失灵 | 用空目录继续，只列手填项并带 `note` |
| 2 | 按普通空格拆分 ID | 从网页复制「模型名 + 描述」会拆出十几个垃圾 ID，吃满 12 个验证额度 | 只按逗号/换行分项，每项取第一个 token |
| 3 | 手填 ID **无长度上限** | 12 个超长串把 GET URL 顶到 8KB，换来一个 414 | 单 ID ≤ 200、总原文 ≤ 2500，超长丢弃 |
| 4 | 目录失败的 `note` 前端不显示 | 只看到手填一行，误以为供应商只有这一个模型 | 列表顶部显示 `note` |
| 5 | 验证中切换供应商 | 串行 12×20s 的窗口里很容易发生，把 A 的模型发到 B 去验 | `runVerify` 接收**发起时**的 pid |
| 6 | 连点「验证手填」 | 重复请求，浪费配额、可能触发 429 | `loading` 标志 + 验证中禁用 |
| 7 | 添加 → 保存 → 回市场 | 弹窗整个重建、输入框清空，刚加的模型从列表消失 | `marketManualDraft` 草稿 |
| 8 | 手填新模型的规格是**猜的** | 256K 的猜测被当事实写进配置（11-04 的教训） | 表单明确标「规格未核实（按名字猜的）」 |
| 9 | 参数名 `extra` 含义含糊 | 与 pydantic / 其他语义混淆 | 改名 `manual_models` |

## 未修的已知局限（记录，不在本次范围）

- **verify 只用池里第一把 Key**：第一把没权限、第二把有，会误判「不可调用」。
- verify 是 `max_tokens=1` 的最小请求：能判「能不能调」，判不了「上下文多大、
  支不支持工具」。
- 手填 ID 若与目录 ID 只差大小写，会出现两行（供应商 ID 一般大小写敏感，
  未做归一化）。
- `already_added` 仍按 preset family 判定：已收录模型想加第二个供应商，
  市场不提供入口（既有设计，走编辑模型加部署）。

## 验证证据

- `ruff` / `mypy`（117 文件）/ `pytest` **1253 例**全绿。
- 真实网关（8317）端到端：
  - `?manual_models=moonshotai/kimi-k3.1-pro` → 85 行，手填 1 个
  - `?extra=`（旧名）→ 84 行，被忽略（确认改名生效）
  - 粘贴整行描述 → 正确只取第一个 token
  - 500 字符 ID → 丢弃，只留合法项
  - 经网关 verify → `not_found / ok=false`（该账号 NVCF 权限未开通，与功能无关）
- 新增回归 5 条 + 前端守卫 3 条（cap 一致性、规格警告、草稿保留 / note 展示）。

## 结论

功能可以同步。唯一需要提醒的是：**控制台静态文件没有版本号**，同步后运营者
要强制刷新（Ctrl+F5）一次，否则浏览器可能还在跑旧 `console.js`，手填时会发
旧参数 `extra`，看起来像"功能没生效"。
