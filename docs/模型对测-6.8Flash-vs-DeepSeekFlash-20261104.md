# 模型对测：sensenova-6.8-flash vs deepseek-flash（V4.1 Flash 1017）

日期 2026-11-04。全部直连商汤官方端点（`token.sensenova.cn`）实测，
绕开网关路由，避免"哪条腿被选中"污染结论。可复跑的脚本在 `data/bench/`，
逐次日志与结果在 `docs/对测-20261104/`。

## 一句话结论

**6.8-flash 是"重活机"，deepseek-flash 是"快枪手"。**
同为商汤公测免费档，能力上 6.8-flash 更稳（指令遵循、长文要点更全），
但它 **每次回答都要先想 1000~5000 个输出 token**，中位耗时是 deepseek-flash 的
**8~10 倍**（28.3s vs 3.8s）。日常机械活（JSON 抽取、工具调用、短改写）用
deepseek-flash；长链路、复杂交付、要它想清楚再答的，才轮到 6.8-flash。

## 一、先回答"为什么当初没核对官方文档"

三个原因叠在一起，缺一个都不会出这个事：

1. **预设表里没有 `sensenova-6.8-flash`**。于是 `preset_for()` 落到
   `guess_from_name()`——按名字猜 256K、猜能力分、`spec_source="estimated"`。
2. **商汤自己的 `/v1/models` 目录报的是错的**：`context_length: 262144`。
   而官方文档写「支持 1 M 上下文窗口」。旧规则是"探测压过预设"，
   于是一个 1M 模型被填成 256K——**低估窗口不报错**，只会让长请求在网关这层
   被 `context_fits` 判死、静默降级到更烂的渠道。这才是真正危险的方向。
3. **没有任何机制把"目录与文档不一致"摆到运营者眼前**。市场表格只显示
   "实测 / 预估"两枚标签，两个都是错的（"实测"其实是实测了一个错值）。

已修三处：

| 改动 | 文件 | 说明 |
|---|---|---|
| 补预设 | `app/models/presets.py` | 1M / 64K 默认 128K 上限 / 六档 / 坑写进 `spec_notes` |
| 改优先级 | `app/api/admin/providers.py` | 两者都有时**取大的**，分歧挂 `context_window_conflict` |
| 摊到界面 | `app/web/console.js` | 市场表格显示「⚠ 目录与文档不一致」+ 悬浮说明 |

回归测试 6 条：`tests/test_presets.py` 3 条（1M 窗口、不收 `none`、别和 Lite 混）、
`tests/test_config_write_through.py` 2 条（陈旧的目录值不能缩小官方窗口、
更大的目录值仍要赢）。

## 二、官方规格（已核对，并存进预设）

| 项 | sensenova-6.8-flash | deepseek-flash（V4.1 Flash 1017） |
|---|---|---|
| 上下文 | **1,048,576** | 1,048,576 |
| max_tokens | 默认 65,535 / 上限 **131,072** | 默认 131,072 / 上限 **393,216** |
| 思考档位 | minimal / low / medium / high / xhigh / **max**（默认 high） | none / low / high / max（默认 high） |
| 能否关思考 | **不能**（传 none / disabled 不报错，但思考泄进 content） | 能（`reasoning_effort=none`） |
| 图像输入 | 支持 | **不支持**（目录报 `input_modalities: ["text"]`） |
| 工具调用 | 支持 | 支持 |
| 结构化输出 | 支持（`response_format`） | 支持（json_object / json_schema / text） |
| 价格 | 公测免费（积分制） | 公测免费（积分制） |

### 实测校正的两处

- **上下文 1M 是真的**，不用信目录的 262144。塞 **1,047,678** prompt tokens 返回 200，
  1,049,xxx 才 400。目录值纯属过期。
- **"不能关思考"是真的，而且比文档写的更坑**：文档说 `thinking.type` 只支持
  `enabled`，实测传 `disabled` 或 `reasoning_effort=none` **都不报错**，
  `reasoning_tokens` 也确实为 0——但正文变成
  `"Here's a thinking process: ..."` / `"France's capital is Paris.</think>Paris"`，
  即思考搬进了 `content`。对客户端是脏回答，不是"省了思考"。
  **所以档位表刻意不列 `none`**（预设里写了理由，测试钉住）。

## 三、能力对测（5 类任务 × 3 档 × 3 轮）

题库贴近你的实际负载：JSON 结构化抽取（刀具询价 → 字段）、工具调用（查客户未发货订单）、
铣削参数计算（vc / f / vf）、硬约束改写（恰好 3 句 / 不含"我们" / ≤120 字）、
316L 深孔钻领域知识。全部自动判分，不用"看着还行"。

**满分 15 次（5 任务 × 3 轮）：**

| 模型 | 档位 | 通过 | 中位耗时 | 中位首字节 | 中位输出 token |
|---|---|---|---|---|---|
| **sensenova-6.8-flash** | low | **15/15** | 25.4s | 4.0s | 1416 |
| **sensenova-6.8-flash** | high | **15/15** | 28.3s | 4.2s | 1578 |
| **sensenova-6.8-flash** | max | 14/15 | 32.0s | 3.8s | 1866 |
| **deepseek-flash** | low | **9/9** | **2.7s** | **0.8s** | 120 |
| **deepseek-flash** | high | **6/6** | **3.8s** | **0.9s** | 273 |
| **deepseek-flash** | max | **10/10** | **3.3s** | **0.7s** | 397 |

> deepseek-flash 的样本量少，是它的 429 限流更狠（同样 8 把 Key、每分钟 3 次，
> 它频繁报 `EndpointRPMExceeded` / `EndpointTPMExceeded`，重试 8 次仍打不进去）。
> **这本身是一条结论**：在同样的 rpm 规则下，deepseek-flash 的有效可用容量明显更低。
> 凡标 `ERR exhausted retries` 的不计入通过率，不当作答错。

**唯一一条失分**是 6.8-flash 在 `max` 档写领域知识答了 1867 汉字（限 350 字），
越到高档越啰嗦——它把"想得多"变成了"写得多"，这是真实短板。

### 逐项对比（同档 high）

| 任务 | 6.8-flash | deepseek-flash | 差距 |
|---|---|---|---|
| JSON 结构化 | ✅ 19.8s / 1202 tok | ✅ 2.2s / 194 tok | 慢 9× |
| 工具调用 | ✅ 2.7s / 28 tok | ✅ ~2.0s / 177 tok | 平 |
| 参数计算 | ✅ 26.7s / 1876 tok | ✅ 4.0s / 498 tok | 慢 6.7× |
| 指令遵循 | ✅ 31.9s / 1984 tok | ✅ 6.8s / 791 tok | 慢 4.7× |
| 领域知识 | ✅ 46.7s / 3618 tok | ✅ 16.5s / 1181 tok | 慢 2.8× |

**注意输出 token 那一列**：同样的题，6.8-flash 吐 3~6 倍 token，绝大部分是思考。
在积分制下这不是"免费"——**积分按 token 扣**，所以它的真实单位成本约是
deepseek-flash 的 3~6 倍，只是账单以积分而非美元呈现。

## 四、长上下文检索（这是两个模型都号称 1M 的关键项）

在一段车间记录里埋一个针（"仓库 C 区第三排的货架编号是 QL-8820"），
按深度插入，问编号。两模型均命中：

| 目标规模 | 6.8-flash（high） | deepseek-flash（high/low） |
|---|---|---|
| ~21k prompt | ✅ 35.0s | ✅ 1.6s |
| ~87k prompt | ✅ 31.3s | ✅ 3.0s |
| ~288k prompt | ✅ 95.3s | ✅ 6.3s（5% 深度 7.3s / 95% 深度 5.4s） |
| ~649k prompt | ✅ 181.4s | ✅ 7.4s |
| ~632k prompt | — | ✅ 7.4s |

6.8-flash 另做了位置敏感性（400k 规模）：针在最前 150.1s、在最后 15.4s，
**都命中**——长文里没有"中间丢失"，但它对位置极其敏感，前半段信息会让它想很久。

**结论**：两边 1M 都不是虚标，检索都可靠。差别在**长文下的墙钟**——
deepseek-flash 在 65 万 token 上下文里 7.4 秒答完，6.8-flash 要 3 分钟。

## 五、必须知道的三个坑（配置里已写注释）

1. **思考 token 与正文共享 `max_tokens`**。预算 2048 + `high` 时，思考吃光全部配额，
   `finish_reason=length` 且 `content` 为空——客户端收到 HTTP 200 但一个字都没有。
   实测 1024/2048 都复现，8192 起正常。部署里 `max_output_tokens: 65536` 是安全的。
2. **thinking 泄进 content**（见上）。别给 6.8-flash 配 `none`。
3. **它很啰嗦**。`max` 档尤其明显。要严格字数限制的任务，`low` 档反而更听话。

## 六、怎么用

`config/models.yaml` 已加 `sensenova-6.8-flash`（部署 `sen68-flash-sensenova`，
priority 110，`reasoning_effort: high`，`max_output_tokens: 65536`）。
**没有放进任何别名链**——`zk-auto` 打头还是 `deepseek-flash`（快），
要长链路/复杂交付时**点名** `sensenova-6.8-flash`。

理由：别名的语义是"帮我选"，而按上面的数据，6.8-flash 进链首会把每个请求的
中位耗时从 3.8s 拉到 28.3s；放在链尾又基本轮不到。**它的正确用法是显式点名**，
就像 `glm-5.3` 那样。
