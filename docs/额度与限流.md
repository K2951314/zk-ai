# 额度、限流与凭据池（从 AGENTS.md 拆出，2026-11-26）

> 规则结论以 `AGENTS.md` 为准；这份保留**判据、实测数字、调参细节**，排查 429 /
> 额度耗尽 / 整池真空时才翻。

## 商汤额度与窗口

- 积分池：flash-lite 扣完专属池会**静默**溢出扣通用池（kimi-k3 的积分），API 无
  任何池信号；消耗器靠按积分记账 + 预算熔断防溢出，勿轻易关预算。
- 窗口刷新默认按滚动记账；控制台显示的每账号「重置时间」可能是固定锚点
  （判定方法见使用手册），确认后用 `--anchors "1=HH:MM;..."` 切固定窗口爆发模式。
- 额度按**账号**算：01+02 同账号，07~09 归属待核对；额度上限见 providers.yaml 注释。
- **2026-10-27 额度翻倍，改配置必须同步三处**：5h 6万→**12 万**、周 60万→**120 万**。
  三处是：①`providers.yaml` 的 `rate_limits`（token 口径，5h 3亿→**6 亿**、
  周 30亿→**60 亿**）②`burner.yaml` 的 `window_credits`/`weekly_credits`
  ③`scripts/burn_sensenova.py` 的 `DEFAULT_WINDOW_CREDITS`/`DEFAULT_WEEKLY_CREDITS`。
  只改前两处不够——配置键缺失会回落到代码常量，出现「控制台按旧线画、脚本按旧线停」。
- `config.get(x) or 默认值` 会把合法的 **0** 当缺失换掉（额度写 0 是「不限制」的
  明确意图），必须用 `is None` 判缺失。

## tpm/rpm 桶按账号，不是按供应商

- **2026-09-28 实测推翻旧结论**：同一时刻账号 04/05 以并发 16 稳定烧穿，而
  03/06/07/08/09 全部 429 → `cooldown.throttle_scopes` 的 `quota`/`throughput`
  默认是 **account**，不是 provider。
- 曾按「账号间共享」判成 provider，代价很重：网关一次 kimi-k3 撞 429（那把 Key 与
  消耗器共用同一账号）→ 8 把 sensenova 全部停靠 52s，其中 6 个账号本来健康 →
  请求去打已经超时死的 nvidia → 客户端十几分钟收不到任何字节。
- **网关和积分消耗器共用同一批商汤 Key**（`sensenova-02` 与消耗器 `only:` 都是
  `SENSENOVA_API_KEY_0x`）。2026-10-27 起消耗器已停用（`burner.yaml` 的
  `disabled: true`），所以现在看到 429 就是**纯 tpm 容量问题**，别再往消耗器上想。

## 429 分类与作用域

- 分类器按正文分 `ThrottleKind`：`quota` 额度用尽 / `throughput` tpm /
  `frequency` rpm·rps / `unknown`。
- `cooldown.throttle_scopes` 决定冷却覆盖到哪：`credential` 只冷这把、
  `account` 同 `account-*` 标签一起冷、`provider` 整个供应商一起冷并直接故障转移。
- 现役 `quota` 是 `account`、`throughput` 是 `credential`（2026-10-08 改：9 把 Key =
  9 个独立账号，一把 429 只冷这把，让其余 8 把继续被试）。
- 判「换 Key 还是换部署」只看 `CredentialPool.effective_throttle_scope()` 一个方法，
  池子与调度器共用，否则两边判断会漂移。

## rpm 桶与主动闸

- **2026-10-13 实测**（服务器 DB + 本机 DB 双口径）：服务器近 3 小时每把 Key 每分钟
  被打 3~6 次，**429 率 80%、04:56 起连续 3 小时无一把 Key 恢复**；本机 7 天 459 次
  成功里每 Key 实际通过的 rpm 中位 2、p90 6、p99 8、最大 8，从没突破 8。
  且 429 时 prompt 中位数不足 5k tokens——**不是 tpm 打爆，是账号级 rpm 惩罚**。
- **主动 rpm 闸**：`providers.yaml` 的 `options.rate_limits`
  `{scope: account, window_seconds: 60, max_requests: 3}`——**事前**让配额见底的 Key
  出列换下一把，而不是撞 429 才事后惩罚。取 3 不取 6：超发会被商汤惩罚数小时，
  保守的代价只是排队几十秒。扩容新 Key 时按同比例上调（每把独立计）。
- 回归测试 `tests/test_limits.py` 的
  `test_sensenova_has_a_tuned_rpm_rule_in_real_config` 与
  `test_the_rpm_rule_actually_gates_in_the_limiter`。
- ⚠ **「rpm 惩罚」不能解释 2026-10-24~25 的整池瘫痪**：那两天每把 Key 每分钟只发
  **1.2 次**（远在 rpm 3 之下），9 把从 04:29 到 15:33 连续 429、一次没恢复
  （每把 81~91 次）；同批请求平均 **18.7 万 token**，`tpm/rpm` 混合报错 577 次。
  结论：**小 prompt 时是 rpm 惩罚，长上下文时是 tpm**；同一个 `max_requests: 3`
  对后者无效。判据是「每分钟请求数 vs 每请求 token 量」，别只量前者。

## 单请求扫池与整池真空

- `retry.max_credentials_per_deployment` 曾是 **9**（等于池大小）：一个请求按序扫完
  9 把、每把 429 挂 60s → **整池瞬间真空**；紧接着的请求在 `/credential` 阶段
  0.01 秒返回 `no_available_credential`，上游一次没发。实测 154 条失败里
  **55 条（35.7%）是这个形状**。已降到 **3**（商汤 9×3=27 req/min vs 客户端峰值
  10 req/min，容量够，缺的是让渡）。回归 `tests/test_limits.py` 钉配置值 = 3。
- `_wait_for_credential` 在整池冷却时先等（上限 10s、不越过墙钟）再重取。
  ⚠ **实测救 0 条**：那 55 条瞬时 503 之后，下一个商汤成功的中位等待是 **333 秒**。
  它只是兜底（避免 0.01s 空跑），**不是解药**；解药是容量（充值/加账号/分流）。
- `only_leg`：链上最后一条可用腿可扫完整池（`_is_only_fallible_leg`）。让渡的前提
  是还有别的腿可退；这是 2026-11-13 的正确设计，不是上限没生效。

## 墙钟与单腿超时

- **`max_total_attempts` 是次数上限，不是时间上限**（`ZKAI_MAX_REQUEST_SECONDS`，
  默认 300s）：20 次 × 60s = 最坏 20 分钟。墙钟预算只在**两次尝试之间**检查，
  不会打断已在飞的流（那会截断客户端还能读的响应）。
- **单条慢腿能吃光整个请求**：实测一次 AMD 尝试跑 701 秒，而预算只有 300 秒——
  48 条失败（31%）就这么死的。已加 `retry.attempt_timeout_floor`（默认 20s）+
  `attempt_timeout_margin`（5s）：每次尝试读超时 =
  min(provider 超时, 剩余墙钟 ÷ 剩余部署数 - margin)。**floor 是硬下限**：给
  100k prefill 切 15 秒等于「每家都失败」，比原来的病更糟。`0` 回到旧行为。
- 误杀评估：商汤 227 次成功**全部在 30 秒内**，145 秒时间片误杀率 0%。
- ⚠ **管不了链上最后一条腿**（它按定义拿剩余全额预算）。`ds` 链实际只有 2 条可用腿
  （`ds4.1m` 停用），AMD 是最后一条；压到 120s 会丢 59 次慢成功（235→176），
  是产品决策。

## AMD 冷 prefill

- 2026-10-24 服务器实锤：`developer.amd.com.cn` 的 DeepSeek-V4.1-Flash 在**未命中
  缓存**时，113k token 的 prefill 全程不吐字节、实测 50-70 秒；`timeout: 60` 会在
  中途掐死——流式一旦开头发送就**无法重试**，客户端整轮报废。
- 判定特征：中途超时的尝试总时长 ≈ X + 60s（实测 60.3/78.4/82.5/122.7/151.2s，
  落差恰为 60）；命中缓存的轮次 prefill 秒过（cached=100%，45-69s 全是生成）。
- 已修 `timeout: 60→300`、`max_retries: 2→0`。⚠ 粘性会话的**首轮（缓存冷启动）
  恰恰是长 prefill 轮**——读超时太紧等于专挑粘性的第一枪打。

## 路由计划硬顶与连接重试

- `retry.max_deployments` 是路由计划硬顶：曾按 zk-k3 的 3 部署估成 4，zk-auto 全链
  6 部署时 DeepSeek/Qwen 进不了计划，坏渠道烧光 `max_total_attempts` → 已改 **8**。
- `ProviderConfig.max_retries` 曾是死配置：字段存在、providers.yaml 给 NVIDIA 设 0，
  但适配器建 `httpx.AsyncClient` 时没读。现已接 `AsyncHTTPTransport(retries=...)`
  （**连接级**重试，不是读重试——挂起仍靠上层冷却+换渠道）。
  `trust_env=True` 必须显式写，替换默认 transport 正是丢掉 Windows 系统代理的方式。
- **NVIDIA `max_retries` 会让挂起重试翻倍墙钟**（60s→120s+/次），已设 0。
