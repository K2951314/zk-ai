## 0. 结论先行（v2）

1. **「频繁中断」不是代码回归，也不是 v1 说的「上游全挂」**。
   服务器 HEAD = 本机最新 `7c89c0b`，工作区未提交改动只碰可观测性面板。
   真机制是：**网关静默 → 客户端 60 秒硬超时 → 499**。证据是 10 条零上游尝试的
   请求耗时整齐落在 **59.74~59.92 秒**（`§2.2`），这是客户端超时，不是上游失败。
2. **「多供应商没用」被 v1 归错了因**。现网 `deepseek-flash` 有 **3 家**、
   `k3.1p` 有 **2 家**，都配了 `round_robin`，且已进内存生效。用户看到"只调用一家"，
   真正原因是三层叠加：
   - **别名策略盖过模型策略**（`router.py:305`）：`ds` 是 `priority`，
     直接把模型的 `round_robin` 废掉，链首永远是 `a-ds`；
   - **`front_model` 钉死轮转**（`router.py:433`）：`zk-auto` 配了临时
     `front_model: deepseek-flash`，每次把它提到队首；
   - **健康状态没进排序**：额度耗尽 9.7 小时的腿仍排队首，被调度器跳过。
3. **v1 最大的问题是"改了一圈却改不到点上"**：它设计的"模型级默认轮转"
   对别名入口不生效，而**所有真实流量都走别名**（`ds` / `zk-auto`）。
   v2 把改动收敛到真正生效的那一层，并删掉三处过度设计。
4. **一个 v1 完全没提、但比什么都重要的约束**：多供应商里混进了
   **已知不可用的供应商**（NVIDIA 全渠道挂死，AGENTS.md 有结论）。
   10:28 之后 `k3.1p` 的 5 次调用全打在 `nvidia`、5 次全 cancelled；
   而同一模型的 `modelscope` 腿一次没被碰到——因为链首是 nvidia。
   **在死腿没剔除之前，加再多供应商都是把请求往坑里送**。

## 2. 事实基线（v2 重新取证）

### 2.1 现网配置真相（三处一致，不再是待核项）

| 入口 | 策略 | 候选链（`/zkadmin/router/preview` 实测） |
|---|---|---|
| `ds`（别名） | `priority` ← **别名**，盖掉模型 `round_robin` | `a-ds`(AMD) → `deepseek-flash-sensenova`(商汤) → `m-ds`(魔搭) |
| `deepseek-flash`（直连） | `round_robin` ← 模型 | 同上三条，但会轮转 |
| `zk-auto`（别名） | `round_robin` + **`front_model: deepseek-flash`** | `m-ds` → `m-k3.1p` → `n-k3.1p` → `a-ds` → `deepseek-flash-sensenova`；front_model 每轮把 deepseek-flash 的腿提到队首 |
| `k3.1p`（直连） | `round_robin` | `m-k3.1p`(魔搭) → `n-k3.1p`(NVIDIA) |

`config_watch.reload_count=0` 但内存态已含三处新部署——说明是**控制台热改直接进了内存**
（`upsert_model` 先改内存再落盘），不是文件监听漏载。**不要**按 v1 的思路去查"哪份是真相"。

### 2.2 中断的真实机制

| 证据 | 数值 |
|---|---|
| 11-26 cancelled | 55 条，全部 UA `undici`、HTTP 499、`error_type=no_stream_meta` |
| 耗时 | 平均 **58.2s**；其中 10 条零尝试的精确落在 59.74~59.92s |
| 逐小时 | 04:00 全绿(98/98)；05–07 集中取消；08–09 变显式 `error`（`b3c4d86` 让无效等待直接故障转移）；10:00 又 14 条取消 |
| 7 天 error_type | `no_available_credential` 951、`rate_limit_error` 879、`no_stream_meta` 451 |
| 典型 499 的 attempt 链 | 商汤 3 把 Key 依次 429 → 魔搭无 Key（**34815s** 后恢复）→ 无首块 → `meta=None` → `request_service.py:425` 记 `no_stream_meta` → 58s 后 499 |

**因果链**（v2）：上游额度打满 → 调度器在预取窗口内反复故障转移、迟迟不给首字节 →
`stream_prefetch_timeout=10s` 到点返回 200，但 `undici` **不在心跳白名单**
（`chat.py:91-104`，只有 codex / deepseek-harness / openai-*），于是 `ping_every=None`
→ `chat.py:354-368` 的 `asyncio.wait(..., timeout=None)` 纯等，
再无任何字节 → 客户端 60s 硬超时断开 → `GeneratorExit` → `cancelled=True` → 499。

- 11-23 文档 `docs/harness中断根因-20261123.md:143` 判断「undici 不依赖心跳」，
  **本次数据推翻**：2490 条 undici 请求里，它恰恰是 499 的唯一主体。
- `WorkBuddy/5.9.4`、`ZCode`、`qoder` 等 UA 在服务器上都有独立字符串，
  **不是 undici 的子串**，所以把 `undici` 加进白名单不会污染 WorkBuddy 输出
  （v1 担心的"会不会误伤"已排除）。
- 但 `no_stream_meta` 这个归因仍要修：`cancelled` 分支应该记 `client_disconnected`，
  `no_stream_meta` 只留给"流真的没产出 meta 且非客户端断开"。

### 2.3 "只调用一家"的三层真因（重新归因）

**L1 策略层（决定性）**：`ds` 别名 `priority` 把模型的 `round_robin` 盖掉，链首永远 `a-ds`。
`zk-auto` 虽是 `round_robin`，但 `front_model` 每轮把 deepseek-flash 的腿插到队首
（`router.py:433`），跨模型分担被压掉。**用户加的供应商确实在链里，只是永远排不到第一。**

**L2 可用性层（比策略更要命）**：10:28 之后 `k3.1p` 5 次调用全打 `nvidia n-k3.1p`、
5 次全 cancelled，同模型的 `m-k3.1p` 一次没上。NVIDIA 全渠道挂死是 AGENTS.md 的既有结论。
**加供应商之前不做可用性实测，等于给故障转移链加了一条死腿。**

**L3 健康层（次要）**：`unavailable_deployments()` 只用于 `_promote_front_model`
（`router.py:308`），没传给 `strategy.order()`（`router.py:307`）。冷却/隔离中的腿仍可能在队首，
被 `scheduler.py:691-695` 跳过，白费一次首跳判断。注意这只覆盖**部署级短冷却**；
魔搭 9.7 小时的额度耗尽是**凭据级长冷却**，走 `pool.next_available_in()`，
是另一条信号，不能混为一谈（v1 在这里合并错了）。

**L4 写入层（隐患，非本次现象）**：`models.py:79-96` merge 分支跳过
非 merge 分支的 provider 存在性校验与 deployment id 去重（`models.py:106-127`），
拼错的 `provider_id` 会静默落盘、运行时被 `router.py:280-287` 用 `debug` 跳过。

## 3. 方案 v2

设计目标不变：把**静态故障转移列表**升级成**活的供应商池**——
平时分担（多家轮流接活）、出事互备（健康的顶上）、全程可见。
但改动**收敛到真正生效的那一层**，优先级按"先止血、再修机制、最后做体验"排。

### 3.1 P0 止血：先让已有配置生效（几乎零代码）

| # | 改动 | 位置 | 为什么是 P0 |
|---|---|---|---|
| P0-1 | `ds` 别名 `strategy: priority` → `round_robin` | 服务器 `models.yaml`（**需单独授权**） | 一行配置就让 `deepseek-flash` 的 3 家开始轮转；v1 想改代码解决的问题，其实先在这里 |
| P0-2 | 处理 `zk-auto` 的 `front_model`：它是 11-23 23:15 的**临时**措施（YAML 注释自己写了"还原只需改回 k3.1p"），已挂 3 天 | 服务器 `models.yaml`（**需单独授权**） | 不去掉它，任何分担策略对 `zk-auto` 都无效。先确认 front_model 是否还要；要保留就显式标注"钉住期间不参与分担"，不做隐式覆盖 |
| P0-3 | `nvidia` 腿从 `k3.1p` 摘掉（`enabled: false`）或隔离 | 服务器 `models.yaml`（**需单独授权**） | 死腿剔除前，分担只是把请求摊到坑里。先用 `/zkadmin/router/preview` + 一次真实请求复核，别只看目录 |
| P0-4 | 同模型多部署时，控制台「＋添加」成功后**立即跑一次可用性验证**（真实 chat 请求），失败就提示"这家暂不可用" | `app/web/console.js` / `app/api/admin/models.py` | 复用 AGENTS.md「只有实测算数」的既有结论，防止再添加死腿；不新建探测框架 |

> P0 的三项配置都**只在服务器现役文件**上动，本机 `models.yaml` 保持历史快照，
> 避免把旧配置误当真相写回（v1 的 A1 教训）。

### 3.2 P1 中断修复（确定性，本机 dev）

| # | 改动 | 文件 | 说明 |
|---|---|---|---|
| F1 | `undici` 加入心跳白名单 | `chat.py:91-104` | **本次 55 条 499 的直接修复**。优先走已有的 `sse_comment_user_agents` 配置通道（无需改代码即可热更），代码白名单作为兜底；WorkBuddy 等已核实不是 undici 子串，不会污染 |
| F2 | `cancelled` 且无明确 error_type 时记 `client_disconnected` | `request_service.py:421-430` | `no_stream_meta` 只留给非客户端断开；控制台已有该中文映射（`console.js:745`） |
| F3 | 服务器 `config.yaml` 显式补 `stream_prefetch_timeout: 10` | 服务器（需单独授权） | 代码默认已是 10，显式化只为可审计；`config.example.yaml:63` 已有该键 |

⚠ **F1 不是万能药**：它解决的是"客户端别在 60s 主动断"，不解决上游没额度。
心跳之后客户端会继续等，直到网关给出终态错误或 `max_request_seconds=300` 兜底。
所以 F1 必须配合 P2-2（让全链失败尽快给出明确的流内 error 事件），
否则体验会从"58 秒中断"变成"等 5 分钟才报错"——**这是 v1 完全没考虑的反效果**。

### 3.3 P2 机制：健康进入排序 + 策略冲突显式化

**P2-1 冷却/隔离进排序。**
`Router.plan(..., unavailable=...)` 已拿到集合；把它作为 `RoutingCandidate.penalized`
写进候选（Router 依旧不做 I/O），各策略排序键加惩罚项：可用的在前，
`unavailable` 的**降到队尾但不删除**（保留链完整性，避免全冷却时无候选）。
冷却解除后自动回池。注意 `front_model` 提升（`router.py:425-433`）必须同步尊重这个标记，
否则降权会被一次 `insert(0, ...)` 抹掉。

**P2-2 凭据池健康与部署健康分开处理（修正 v1 A5）。**
- 部署级：`unavailable_deployments()` → P2-1 的降权。
- 凭据级：`pool.next_available_in(provider_id)` 返回"整池要等多久"。
  当它 > 阈值（复用 `b3c4d86` 的 `_MAX_WAIT_BEFORE_FAILOVER=10s`）时，
  把该 provider 的候选整组降权，而不是等调度器在 `scheduler.py:691-695` 逐个跳过。
- 两者是**不同信号、不同通道**，不要合并成一个"健康分"。
- 同时让全链失败尽快产生终态 `error` 事件（配合 F1，见上）。

**P2-3 策略冲突显式化（v2 核心，替代 v1 S2）。**
`router.py:305` 现在是 `alias.strategy > model.strategy > 默认`，别名静默盖掉模型策略。
改成：
1. 当别名与候选模型的 strategy 不一致时，**在 `routing_reason` 里明说**
   `alias_strategy=priority overrides model_strategy=round_robin`，
   并让 `/zkadmin/router/preview` 与控制台模型页显示这条警告；
2. `strategy` 的最终裁定放在**候选集**上，而不是"哪个对象先被查到"：
   别名链（跨模型）与模型内多部署（跨供应商）是**两个独立的可分担池**，
   各自按自己的策略轮转，再拼接成候选链。这样 `ds` 即使别名是 priority，
   模型内的 3 家仍能分担——**这才是用户真正要的"同一模型多供应商都干活"**；
3. `front_model` / `pin_first` 提升时，若目标是"分担池"成员，
   只在本轮把它参与的池内轮转位置提前，**不跨池破坏其他池的轮转状态**。

**P2-4 修 `RoundRobinSelection` 的 cursor。**
`strategy.py:239` 用 `eligible[0].model.id` 当 key——轮转后 `eligible[0]` 会变，
key 跟着漂移；且多进程不共享。改为稳定池标识（池内 deployment id 排序后的签名），
并加一条测试钉住"连续 N 次请求覆盖池内每一家"。

### 3.4 P3 可见性（修正 v1 A6 的数据源）

- **数据源改为 `request_attempts`**：11-26 该表 1118 行 `deployment_id` 零缺失；
  而 `requests` 表对 `cancelled`/`error` 的 `deployment_id` 是 100% NULL。
  按 `request_attempts` 聚合每家的尝试数、成功率、429 数、平均延迟，
  再加 `health.quarantined_deployments` 显示隔离/冷却状态。
- 控制台模型页每个 deployment 旁显示这些数字 + "当前是否可用"；
  复用 `/zkadmin/router/preview`（`models.py:186-223`，已返回候选链与 pool）
  加「预演这一跳」按钮，显示"现在会先打谁、谁被跳过、为什么"。
- **策略冲突警告**（P2-3 第 1 点）也在这一页展示。
- 不新增监控面板/图表库，沿用 `console.js` 现有表格与中文提示守卫。

### 3.5 P4 写入校验与体检（修正 v1 的过度设计）

- merge 分支（`models.py:79-96`）补齐非 merge 分支的两项校验：
  provider 存在性、deployment id 去重；校验失败 400 且不落盘。
- `scripts/check_config.py` 增一条**只读告警**：
  「同一模型多 deployment，但所属别名是 `priority`/`capability` 且会盖掉模型轮转」→ 警告。
  **删掉 v1 S4 里"自动改默认策略"的行为变更**——静默改策略会改变成本结构，
  且 `config_watch` + DB 镜像三处同步容易漏，属于过度设计。

### 3.6 与既有机制的冲突（v1 完全没提，必须写清）

| 既有机制 | 与「分担」的冲突 | 处置 |
|---|---|---|
| `credential_affinity.enabled=true`（`config.yaml:52`，TTL 1800s） | 同一会话钉住上次成功的 Key，目的是命中供应商侧 prompt cache；跨请求轮换部署会**打断缓存、抬高 prefill 成本** | 分担粒度用**会话/请求组**而非单个请求；或只在同一 provider 内轮换 Key、跨 provider 轮换按会话边界。本次先显式记录该取舍，**不改变 affinity 默认行为** |
| `max_credentials_per_deployment=3`、`max_total_attempts=20`（`config.yaml:70,79`） | 池子变大后，单请求扫更多家会更快耗尽尝试预算 | 分担只改"谁先上"，**不放宽预算**；P2-1 降权反而减少无效尝试 |
| `quota_cooldown` 到次日 00:00（34815s） | 长冷却腿必须整组降权，不能每次都试一遍 | P2-2 的凭据级信号 |
| README 三处「N 个用例」由 `test_doc_scale` 核对 | 新增测试会让守卫变红 | 每次加测试同步改 README 三处数字（既有门禁） |

## 4. 明确不做

- 单请求并行 fan-out 到多家（双倍烧配额、结果不一致、要合并策略）。
- 主动探测上游额度余量（上游无信号，只能靠失败冷却 + 一次性实测）。
- **静默改默认策略 / 自动改权重**（v1 S2、S4 的做法，会悄悄改变成本结构，且三处配置同步易漏）。
- 把部署级冷却与凭据级长冷却合并成一个"健康分"（信号语义不同）。
- 默认给所有 UA 发心跳（WorkBuddy 会把 `: ping` 当正文显示）。
- 修容量本身（补额度 / 等魔搭每日重置是运营动作，不是代码动作）。
- **服务器同步不在本次范围**；P0/F3 的每一项都需要单独授权。

## 5. 实施顺序与门禁

1. **P0 配置三项 + F3**：需服务器授权，逐项改、逐项用 `/zkadmin/router/preview`
   与一次真实请求复核；改前保留 `.bak-*`（`config/*.bak-*` 只留基线 + 最新可回滚点）。
2. **F1/F2 + 回归测试**：本机 dev，先加"undici 收到心跳且不再 58s 断"的用例，
   变异验证（撤掉 F1 必须变红）；F2 补归因断言。
3. **P2-1 → P2-2 → P2-3 → P2-4**：每步单独跑测试，P2-3 要覆盖
   "`ds` 别名 priority 下，模型内 3 家仍能分担"这条关键回归。
4. **P3 → P4**：可见性与校验。
5. **门禁**：`ruff check app tests scripts` + `mypy app scripts` + `pytest` 全绿；
   `git diff --check`；暂存清单核对不含 `.env` / 现役 config yaml / db / `data/`；
   新增用例同步 README 三处数字；前端改动做真机截图或计算样式核查
   （守卫全绿抓不到 JS 语法错）。
6. **失败回滚**：每步一个 commit；服务器配置改动留 `.bak-*`；本机未同步服务器可独立回退。
