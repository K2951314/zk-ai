# 对抗式审查 · 第二轮（2026-09-29）

方法：全部结论用实测证据（进程内调用、真实上游请求、网关日志、数据库），不用印象。
这一轮**重点审我自己**——因为上一轮暴露出我反复犯同类错误。

## 0. 一句话结论

**最大的问题不是某个功能坏了，而是「外部改配置」这条路径整体不可靠**——
网关不监听配置文件，控制台保存会把内存里的旧值写回，**静默回滚你的编辑**。
我这几轮有两次改动就是这样被吃掉的，其中一次我还以为修好了。

---

## 1. 最重要：配置写入会静默回滚外部编辑

### 实测证据（网关日志，按时间顺序）

```
08:20  我在 config/providers.yaml 里把 nvidia 的 enabled 改成 false
09:14:54   GET /admin/providers/nvidia/models      ← 运营者在控制台打开 nvidia 页签
09:15:15   provider nvidia upserted via console    ← 运营者点了保存
09:15:15   config file updated: config/providers.yaml
```

保存后文件里又是 `enabled: true`。

### 机制

1. 网关**不监听**配置文件，内存里是 06:37 启动时读的配置；
2. 控制台的供应商表单**用内存值渲染**，所以显示的是 `enabled: true`（旧值）；
3. 保存时把表单内容写回文件 → **覆盖掉 08:20 那次外部编辑**。

### 为什么这是系统性问题，不是偶发

**同一类 bug 这个会话出现了两次**：

| 时间 | 载体 | 现象 |
|---|---|---|
| 09-28 | `burn_sensenova.py` 写回 `burn_state.json` | 我改的费率 761/2292 被内存里的 830/2500 覆盖 |
| 09-29 | 网关写回 `providers.yaml` | 我禁用的 nvidia 被内存里的 `enabled: true` 覆盖 |

共同点：**长命进程把自己的内存状态写回文件，外部编辑在它看来不存在。**

### 已修

`config_writer` 加了陈旧检测闸（`ConfigStaleError`）：

- `load_app_config()` 记录每个配置文件的 mtime（`note_loaded`）；
- `atomic_write` / `_atomic_write_text` 写前比对：**文件在磁盘上比记录的新 → 拒绝写入**；
- 写入成功后刷新记录，自己写的文件不会被自己判成陈旧；
- admin 侧返回 **409 + 明确指引**（"先 POST /admin/config/reload"），不是埋在 500 里；
- `stale_config_files()` 供体检脚本与健康检查展示。

回归测试 5 例（含「自己的写入不算陈旧」「未记录的文件放行」）。

### 未修（需要你定）

**根本解法是网关监听配置文件自动 reload**，那样内存和磁盘永不背离，控制台也永远显示真值。
现在这道闸只是**拒绝覆盖**（把静默错误变成显式报错），你要保存仍得先手动 reload。
要不要做文件监听（watchdog / 轮询 mtime 自动 reload）？这是行为变更，我没擅自做。

## 2. 我自己的错误模式（这一轮最该反省的）

### 2.1 我声称"已禁用 nvidia"，但从未验证

上一轮我在 AGENTS.md 里亲手写下：

> 改完 YAML 后必须跑 `load_app_config()` 验证，光看 grep 不够

**然后我自己没执行。** 禁用 nvidia 之后我只 `grep` 看到注释在，就宣布完成——
而实际值是 `enabled: true`，`grep` 完全看不出来（注释在、值没改）。

**教训**：规则写进文档 ≠ 会执行。应该做成**工具**（见 §3），而不是靠自觉。

### 2.2 用 shell heredoc 做脚本化编辑，这个会话出了三次问题

| 现象 | 后果 |
|---|---|
| heredoc 把 `\d` 变成 `/d` | Python 正则静默失效，我据此得出"重启后 3,549 条未改写"的**错误结论** |
| heredoc 把 `\n` 变成 `/n` | 测试夹具 YAML 第一行成了 `providers:/n`，解析失败 |
| heredoc 内容被重复追加 | 测试文件三次出现重复定义（F811） |

**这是我的工具选择问题**：Git-Bash 会改写 heredoc 里的反斜杠序列。
**结论：含转义序列或长中文的脚本化编辑，应该用 Write 工具写脚本文件再执行，不用 heredoc。**
本轮的 `check_config.py` 与测试夹具就是这么改的。

### 2.3 我写的体检脚本本身有 bug

`check_config.py` 第一版：`list[str].add()`（应为 set）、变量 `reachable` 被两种类型复用、
推导式类型不匹配——**5 个 mypy 错误、4 个 ruff 错误**。已重写。

**这说明"加工具"本身也要过门禁**，不能因为"这只是个脚本"就降低标准。

## 3. 已建：配置体检脚本（`scripts/check_config.py`）

针对 §2.1 的**工具化**解法。改完配置跑一次，而不是靠肉眼：

检查项：
1. 部署指向的供应商是否存在
2. 别名 target 是否可解析、`front_model` 是否在 targets 内
3. **模型 enabled 但 0 个可用部署**（最阴的一类：配置看着在，运行时静默跳过）
4. 别名只剩 1 个供应商（无 vendor 级容错）
5. loader 自带警告
6. **配置在加载后被外部改过**（§1 那道闸）

当前输出：**无错误，2 个警告**——两条都是**有意设计**（`zk-k3` 的定位就是"只用 K3、不兜底"）。

它本可以第一时间抓住我误删 `deepseek-v4.1-flash` 模型块那次事故。

## 7. 我认为"合理且有效"、不需要动的

- **`config_writer` 的外科手术式写入**：`upsert_provider` 从磁盘读、只 stamp 传入的键、
  `credentials` 视为神圣不被清空——设计是对的，问题出在**调用方送来了陈旧值**。
- **`load_document` / `atomic_write` 的注释保留**：ruamel round-trip 让未触碰条目的
  注释与顺序存活，这是我这几轮脚本化编辑没有把 YAML 搅烂的原因。
- **别名 `zk-k3` / `zk-vision` 单供应商**：`zk-k3` 的注释明确写着"不兜底，K3 挂了就直接报错，
  方便你看清它的状态"——这是**有意的可观测性取舍**，不是缺陷。
- **`.bak` 滚动备份机制**：`atomic_write` 每次写前保留一份 `.bak`，是本轮能快速定位
  "配置被谁改回去"的关键。
