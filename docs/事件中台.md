# 事件中台：让任务不再从「你打开窗口」开始

> 2026-11-02 落地。规则正文在 `AGENTS.md` 的「事件中台」一节，这里讲怎么用、怎么排障。

---

## 1. 它解决的是什么问题

以前的链路是：**你打开控制台 → 点按钮 → Agent 干活**。
问题是所有事情的起点都在你身上 —— 你不打开那个窗口，什么都不会发生。
不管模型多强，能同时推进的事永远等于你盯得过来的那几个窗口。

现在补上的是前半段：

```
信号（/health 异常、config 漂移、git 落后、PR…）
  → 中台（统一格式 → 语义去重 → 规则匹配 → 落库）
  → 本机 worker 长轮询取走
  → 执行体（cli-skill / cli-grinder…）
  → 结论 + 决策标记
  → 需要拍板才推飞书，否则只落库
```

**你只做最后一步**：在飞书卡片或控制台的「事件流」页上点一下。

## 2. 五层里哪些是新的

| 层 | 状态 | 在哪 |
|---|---|---|
| 信号源 | 已有数据，新增采集器 | `scripts/event_watch.py` |
| 事件中台 | **新增** | `app/services/events/`、`app/api/events.py`、`events` 表 |

**没有新建「选模型」这一层**，这是有意的：

- 事件规则只写 `to: cli-skill`（角色）
- 角色用哪个 CLI、哪个模型、免费还是收费 → `config/cli_tools.yaml`
- 模型走哪个供应商、哪把 Key、失败怎么转移 → `config/models.yaml` + 路由层

所以换模型改一行 `cli_tools.yaml`，换供应商改一行 `models.yaml`，都不用碰事件规则。

> ⚠ **2026-11-02 实测**：本机 `claude` 命令不存在，但 `cli_tools.yaml` 里
> `claude: enabled: true` —— 于是 `cli-claude` 角色被注册表忽略了。
> 规则默认改成 `cli-skill`（codex，自带 `~/.codex/skills`，正好适合「按 skill 处理」）。
> 这本身就是「配置漂移」的一个样本：**enabled ≠ 装了**。装好 claude 后改回即可。

## 3. 三步跑起来

### 第一步：配飞书 webhook

1. 飞书群里「设置 → 群机器人 → 添加机器人 → 自定义机器人」
2. 拿到 `https://open.feishu.cn/open-apis/bot/v2/hook/xxxx`
3. 写进 `.env`（**不要**写进 `events.yaml`，那个文件是给人看的）：

```
FEISHU_WEBHOOK=https://open.feishu.cn/open-apis/bot/v2/hook/xxxx
FEISHU_WEBHOOK_SECRET=            # 开了签名校验才填
```

### 第二步：起采集器和 worker

```bash
# 采信号（盯 /health，变化才发事件）
.venv\Scripts\python.exe scripts\event_watch.py

# 接单（本机常驻，锁屏不影响，休眠会积压但不丢）
.venv\Scripts\python.exe scripts\agent_worker.py
```

两个都支持 `--once` 调试。

### 第三步：在控制台右侧看「事件流」

侧栏「监控 → 事件流」直接嵌在右侧内容区（不再另开标签页）。
独立路由 `/ui/events` 仍可用（外部链接 / 收藏夹 / 单开一窗看），两者是同一份页面。

第一次跑建议手动灌一条事件验证链路：

```bash
curl -X POST http://127.0.0.1:8317/zkadmin/events \
  -H "X-Admin-Token: <ZKAI_ADMIN_TOKEN>" -H "Content-Type: application/json" \
  -d '{"source":"zkai-gateway","type":"health.quarantined","object":"sensenova-03","summary":"测试事件"}'
```

看到 `"matched": true, "rule": "网关健康异常"` 就说明规则通了。

## 4. 事件格式

字段刻意少 —— 来源侧不该为了发个事件去读文档。

| 字段 | 必填 | 说明 |
|---|---|---|
| `source` | 是 | 来源标识，规则按它匹配 |
| `type` | 是 | 事件类型，支持 `pr.*` 这类 glob |
| `object` | 否 | 受影响对象，如 `sensenova-03`、`PR#128` |
| `summary` | 否 | 一句话摘要，直接进卡片标题 |
| `link` | 否 | 跳回原处的链接 |
| `payload` | 否 | 原始 JSON，排查用；`payload.fingerprint` 参与去重 |

**去重键 = `sha256(source|type|object|fingerprint)`**。
`fingerprint` 优先用来源自己给的，没有就用 `object`。
别用整个 payload —— 时间戳和随机 id 会让同一条事件每次都算出不同的键。

## 5. 规则字段

完整带注释的模板见 `config/events.example.yaml`。几个容易写错的：

| 字段 | 容易踩的 |
|---|---|
| `to` | 是**角色**（`cli_tools.yaml` 里的），不是模型名 |
| `dedupe_window` | 同组多少秒内只开一条。网关健康异常 1800 够，PR 可以 3600 |
| `parallel` | 同组同时跑几条。**超出的不丢弃**，留在队列里排队 |
| `tell` | `always` 每条都推 / `needed` 只在需要拍板时推 / `never` 只落库 |
| `silent` | 静默期只落库不推送，会叠加全局 `notify.silent` |
| `ask` | 一句话指令。执行体看不到你的对话，上下文由中台自动拼进去 |

匹配顺序 **就是文件里的顺序，第一条命中即止**。
别指望「最具体的优先」—— 运营者写规则时脑子里就是从上往下。

## 6. 状态机

```
received ──claim──> running ──┬── ok + 不需要拍板 ──> done
   ▲                          ├── ok + 需要拍板   ──> waiting_decision ──人工──> done
   │                          └── 失败             ──> failed
   └── reclaim_stale（认领超时 2400s）
dropped（没命中任何规则，落库待查）
```

- `running` 卡太久会被自动退回 `received`（`ZKAI_EVENTS_CLAIM_TIMEOUT`，默认 2400s）。
  这个值必须大于执行体 `timeout` 上界 1800s，否则正常长任务会被反复抢走重跑。
- 网关重启时会把所有 `running` 重置回 `received` —— 否则 worker 一崩，
  那条事件永远停在「进行中」，看起来像还在跑。

## 7. 决策边界

**必须你拍板**（`[[NEED_DECISION]] yes`）：删数据、停服/重启、花钱、
对外发消息、改产品方向、新建/轮换密钥、改权限、force push。

**Agent 可以自己干完**：只读诊断、查日志、跑测试、开 PR、改自己分支、写报告。

这条边界现在写在规则 `ask` 里（「只读诊断，不要改配置」），
**下一步该抽成独立文件**（`docs/我定的事.md` / `docs/定了不做的事.md`），
让 Agent 每次派单都带上 —— 否则同一个问题会被问第 N 遍。

### 7.1 批准之后会发生什么（2026-11-03 补：闭环）

**原来这里是断的**：`decide()` 只把「【人工决策】已批准」追加到结论、把状态改成
`done` 就结束，没有任何人去执行。后果是「你批准关服务，没有人去关」，
而你以为它关了。

现在 `POST /zkadmin/events/{id}/decision` 默认会**派生一条子事件**：

```text
父事件 health.quarantined（结论：建议关闭消耗器，NEED_DECISION yes）
  → 你点「批准」，note 写「同意」
  → 子事件 type = health.quarantined.decided
     payload = {parent_id, approved: true, note: "同意", verdict: <父事件结论>}
  → 重新走一遍规则引擎 → 命中「网关健康异常-执行决策」→ 派给执行体去干活
```

三条设计约束：

1. **不新建机制**。决策就是一次普通的 `ingest`，规则作者只要补一条
   `types: [xxx.decided]` 的规则，闭环就成立；没补规则时子事件以 `dropped`
   落库，一眼看得出「还没配闭环」。
2. **重复点同一个决定不会开两条任务**（去重指纹含决策内容），
   但「先否决、后批准」会是两条 —— 这正是想要的语义。
3. **`followup: false`** 只记账不派活，用于「这条我自己去办」。

⚠ 子事件是**有写权限**的。规则模板里那条 `to: cli-skill` 配的是
`codex`（`plan` 档，只读），真要让它动手得改 `to`，届时务必确认
该执行体的 `approval_mode` 不是 `bypass`。

## 8. 排障

| 症状 | 先看什么 |
|---|---|
| 事件进来了但没派单 | `state` 是 `dropped` → 没命中规则；`GET /zkadmin/events/rules` 看规则是否加载 |
| 事件一直是 `received` | worker 没跑 / 连不上中台；`claimed_by` 为空就是没人接。**先确认不是 401**：worker 与事件采集器都要带 `ZKAI_ADMIN_TOKEN`（见下） |
| 一直是 `running` | worker 崩了。等 2400s 自动回收；同一事件被认领 3 次仍没交活会判 `failed`，不会再无限重投 |
| 同一件事开了好几条任务 | `dedupe_window` 太短，或来源没给 `fingerprint` |
| 收不到飞书卡片 | `GET /zkadmin/events/stats` 的 `warnings`；多半是 `${FEISHU_WEBHOOK}` 没进 `.env` |
| 半夜没收到 | 静默时段生效（`notify.silent` 默认 `23:00-08:00`）。**静默只延迟、不吞**：补推扫描每分钟捞一次「终态 + 未送达」，静默一过自动补送（2026-11-08 修）；要半夜立即响铃，把 `notify.wake_on_decision` 设 `true`（只对拍板卡片生效） |
| 规则改了不生效 | 规则按 mtime 重读，**下一次事件进来才生效**，不是立刻 |
| 批准了但没人干活 | 缺一条 `<type>.decided` 的规则（子事件被落成 `dropped`），见 §7.1 |
| 采集器跑了但一条事件都没发 | 先看有没有 `⚠ 没有管理令牌` 那行 —— **401 会被静默吞掉**（见下） |

### 令牌：`.env` 不会自动进进程环境

`ZKAI_ADMIN_TOKEN` 只有跑过 `load_app_config()` 之后才在 `os.environ` 里。
`agent_worker.py` / `event_watch.py` 都在 `main_async` 里补了一次加载；
**自己写的新脚本要照做**，否则所有 `/zkadmin/events` 调用都会被 401 拒掉，
而且看起来像「这一轮没有异常」。

`/health` 不需要令牌，很容易误判成「连通性没问题」。

`/ui/events` 顶部的卡片会直接显示「等你拍板」「执行失败」的条数 ——
自动化在后台跑，必须让人看见它在跑什么，否则「今天怎么一条都没有」
会被当成系统坏了去查。

## 9. 和参考文章的三处不同（有意的）

| 文章做法 | 这里的做法 | 原因 |
|---|---|---|
| 自建 CI 中台（五步 + 本地虚拟机） | 不自建，五步用 GitHub Actions 编排 | 他是 1000 PR/月、超额要交 50 美金；单人项目 2000 分钟/月够用，自建 runner 的维护成本远大于省下的钱 |
| 飞书自建应用 + 卡片回调 | 群自定义机器人 webhook + 跳转按钮 | 自建应用要 app_secret、要权限、要公网回调验签。第一阶段只做单向推送，10 分钟能通 |
| 规则用 `rules.json` | `events.yaml`，按 mtime 热重载 | 跟项目其他配置一致；改规则不用重启 |

**没做的**：自动化小镇可视化（等 events 表有几百条数据再说）、
自动化用户反馈（原文章作者本人也故意不交给 Agent）。

### 已完成（2026-11-04，借鉴 Agent-Autoloop）

读了卡兹克开源出来的 [agent-autoloop](https://github.com/KKKKhazix/agent-autoloop)
（内核 1651 行、零运行时依赖、四个核心机制）。**没有照搬它的架构**
（它是 Node + 零依赖 + 无数据库服务，为「一台 Mac 一条命令跑起来」设计；
本项目有 FastAPI/SQLite/控制台/模型路由，换过去等于丢掉路由层），
只取了四条能直接落下、且不做会出事的：

- ✅ **跳数熔断（TTL）**：`events.hops` + `events.parent_id`，深度由**中台**算
  （事件体里写的 hops 一律不认，执行体不能自己赦免自己），上限
  `ZKAI_EVENTS_MAX_HOPS`（默认 8），超了只落库为 `failed` 并推卡片。
  **人工拍板也算一跳**（不清零）——否则「批准→执行体又发事件→再批准」能无限绕。
  派生事件的去重键里带 `parent_id|hops`，否则同对象的链路会被 30 分钟窗口吃掉，
  hops 永远停在 0、熔断形同虚设（这条是写测试时才发现的）。
- ✅ **交活幂等**：`complete()` 先比对状态与结论。已结束 + 结论相同 = 同一次交活
  （网络断了 worker 会重交），只回一声；结论不同**不覆盖**，保留第一份并记 WARNING。
  原来无条件覆盖，重交会盖掉结论、把 `cost_tokens` 清零、刷新 `ended_at`。
  顺带收紧 `decide()`：只对 `waiting_decision` 生效，已结束的再点一次直接忽略。
- ✅ **回执契约**：Agent 在最后一条消息末尾附 ```` ```zkai ```` 代码块，
  用 JSON 说清要中台做什么（``ask`` 要人选项 / ``notice`` 只通知 /
  ``resolve`` 结卡片 / ``later`` 约时间 / ``events`` 派生下一件事）。
  比一个布尔位的 `[[NEED_DECISION]]` 表达力强得多，且**全部是结构化意图**，
  不靠解析自然语言。解析器**容错优先**：回执坏了正文照用，问题写进
  `receipt.problems`，绝不因一份坏回执丢掉整份结论。
  ⚠ **当前接通程度**：`ask` 用来判 `need_decision`、`later` 与 `events` 已执行；
  **`notice` / `resolve` 只解析、没有消费方**（见待办 3）——别以为写了就生效。
- ✅ **约时间复查（later）**：`event_laters` 表。到点前事件留在库里但
  **不占进程、不花 Token**；到期由 `event_watch.py` 调
  `POST /zkadmin/events/later/drain` 转成标准事件（**取走即消费**，
  两步做会丢）。同一个 `key` 再约一次是改期（旧记录转 `superseded`），不是排两条。

⚠ **时区坑（2026-11-04 实测，已修并钉成测试）**：SQLite 的 DateTime 列**丢时区**
—— 写 `2026-11-04 03:48+00:00` 读出来是 naive 的 `03:48`。仓库层所有比较都用
`utcnow()`（UTC），所以回执里的 `at` 必须**归一化成 UTC 再存**。按本地时间存
（`11:48`）读出来当 `11:48`，跟 `utcnow()=03:48` 一比就凭空晚 8 小时，
**复查永远不会到期**。不带时区的「明天 9 点」按本机时区理解再换算。
