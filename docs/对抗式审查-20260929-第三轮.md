### 1.2 `SENSENOVA_API_KEY` 不在 `.env` 里——换机必丢一把 Key（risk，本轮最重）

- **证据链**（每一环都实测过）：
  1. `config/providers.yaml:56` → 凭据 `sensenova-01`（priority 100，账号 A 主 Key）
     读 `SENSENOVA_API_KEY`；
  2. `.env` 里只有 `SENSENOVA_API_KEY_02`~`_10` + `SENSENOVA_BASE_URL`，
     **没有不带后缀的那把**；它只存在于 Windows 用户级环境变量
     （`[Environment]::GetEnvironmentVariable('SENSENOVA_API_KEY','User')` 取得到）；
  3. `scripts/migrate.py:111` `_secrets_files()` 只返回 `.env` 一个密钥载体，
     导出包里**必然没有这把 Key**；
  4. `app/credentials/pool.py:155`：变量取不到就 `credential ... is not set -> DISABLED`。
- **后果**：换机后网关最重要的那把凭据静默 DISABLED，日志里只会说"环境变量没设置"，
  没人会想到去旧机器补。同类事故本项目已经有过一次（`kimi-k3-moonshot` 空 Key
  产生 3,102 次 `no_available_credential` 噪音）。
- **改法**（四处，都不碰 `.env`、不回显任何值）：
  - `app/core/config.py` 新增 `env_file_names()` 与 `credential_env_gaps(config)`——
    和既有的 `shadowed_env_names()` / `malformed_env_names()` 同一族、同一层。
    现役配置上它精确命中一条：`{'SENSENOVA_API_KEY': ['sensenova-01']}`。
  - `scripts/migrate.py` 新增 `_credential_env_refs()`（**文本扫描**，不用
    `load_app_config()`——配置坏的时候恰恰最需要能导出）+ `_check_credential_envs()`，
    导出前与导入后各检查一次；打印 PowerShell 取值命令但**永远不回显值**。
  - `scripts/check_config.py` 新增两道检查（见 1.4），这条现在就挂在
    运营者每次改完配置都会跑的那条命令上。
- **验证**：`python scripts/check_config.py` 现在输出
  `⚠ sensenova-01 读的 SENSENOVA_API_KEY 不在 .env 里（只存在于 OS 环境变量，本机可用，换机即丢）`。
  新增 11 个测试（5 个 app 层 + 6 个迁移层），含一条**防漂移交叉测试**：
  文本扫描与真解析必须给出同一组变量名，否则有一侧已经看不懂现在的配置。
  做过变异验证：把 `if name and name not in declared` 改成 `if False`，
  3 个测试精确失败。
- **留给你的动作**（红线，我不动 `.env`）：把 `SENSENOVA_API_KEY` 补进 `.env`。
  值不用重新找，从 OS 环境变量里取即可（`check_config` 与导出的提示里都有命令）。

### 1.3 `.migrate_tmp` 是固定路径——并发导出互删中间文件（bug）

- **证据**：这不是推导出来的，是**撞出来的**。本轮跑测试时同一个文件里
  `test_import_asks_the_tray_to_restart_the_burner` 偶发
  `zipfile.BadZipFile: File is not a zip file`；连跑 5 次又全绿。
  根因：`export_package` 用 `_ROOT / ".migrate_tmp"` 这个**固定目录**，
  `finally` 里 `for junk in tmp.glob("*"): junk.unlink()` 把整个目录清空。
  两个导出同时进行（运营者双击导出 + 测试套件在跑）时，
  A 的清理会删掉 B 正在写的 `payload.zip` → 打出来的包在导入端报
  `BadZipFile`，**看起来像密码错了**。
- **改法**：`tempfile.mkdtemp(prefix=".migrate_tmp-", dir=_ROOT)` 每次一个独享目录，
  `finally` 用 `shutil.rmtree(tmp, ignore_errors=True)` 只删自己的。
- **验证**：新增 `test_two_exports_at_once_do_not_corrupt_each_other`
  （两个真线程并发导出，两个包都要能 `testzip()` 通过、都含 manifest、
  且不留临时目录）。该文件连跑 3 次全绿。

### 1.4 `check_config.py` 有两类警告不计入警告数（tooling bug）

- **证据**：`.env` 的值被 OS 环境变量顶掉时，loader 只用 `logging` 打一声
  （出现在输出最上面），**不进 `warnings` 列表**，于是
  `结论：无错误，0 个警告`——而 `--strict`（CI 用）恰恰数这个列表，拦不住它。
  现役机器上就有一条真的：`ANTHROPIC_BASE_URL` 被 cc-switch 设在用户级的
  `http://127.0.0.1:15721` 顶掉（`.env` 里是 28 字符的另一个值）。
- **改法**：新增 `_check_shadowed_envs()` 调 `shadowed_env_names()`，
  与 1.2 的 `_check_credential_envs()` 并列，两件都进警告列表。
- **验证**：现在输出 `警告 2 条`，`--strict` 退出码 1。
- **顺带发现的同族哑雷（已在 §1.6 修掉）**：`config/providers.example.yaml` 原来写的是
  `base_url: ${ANTHROPIC_BASE_URL:-https://api.anthropic.com/v1}`，而 loader 明确支持
  `${VAR}` 插值（`app/core/config.py:94`）。这台机器上 `ANTHROPIC_BASE_URL`
  被 cc-switch 设成了本地代理 → **任何从 example 模板新配的机器，"anthropic"
  供应商的 base_url 会是 `127.0.0.1:15721`**。现役 `providers.yaml` 的 StepFun 是
  硬编码 `https://api.stepfun.com/step_plan/v1`，所以当时没炸；但换机/重装路径上
  这是个哑雷。处理见 §1.6（模板内所有网关自己的开关改成 `ZKAI_` 前缀 + 策略测试）。

### 1.5 `front_model` 只看 eligible，不看健康度（第二轮遗留项，已修）

- **证据**：第二轮审查 §2.2 提的缺陷，HEAD 里仍然如此：
  `app/routing/router.py` 的 `_promote_front_model` 只判 `candidate.eligible`。
  调度器那边其实**会**跳过被隔离/冷却的部署（`scheduler.py`
  `deployment_cooling_down`，两处调用点），所以代价不是"打过去失败"，
  而是**日志撒谎**：`routing_reason` 写 `front_model=X`、`order=[X,...]`，
  而真正第一个被调用的是 Y。这类"文档/日志说谎"正是本项目反复吃亏的地方。
- **改法**（保持 `Router` 不做 I/O 的分层）：`plan(request, *, unavailable=None)`
  接收调度器的健康状态当**纯数据**；`_promote_front_model` 返回
  `FrontModelOutcome(applied, note)`；`Scheduler` 新增
  `unavailable_deployments()`（唯一的健康判断处）并在两个 `plan()` 调用点传入。
  被隔离的接口模型**让位不过滤**——它仍在链里，修好就回来；reason 里写
  `front_model=X(隔离/冷却中，未提升)`，把真相摆出来。
- **验证**：2 个新测试（让位 + reason 不说谎），变异验证：把
  `if unavailable and candidate.deployment.id in unavailable` 改成 `if False`，
  两个测试精确失败。全量 **769 passed**（此前 753）。


### 1.6 供应商接入点用别人家的变量名——`.env` 会被无关工具静默顶掉（risk，已修）

- **证据**：

  3. 现役 `providers.yaml` 的 StepFun 是硬编码 `base_url:`，所以**当时没炸**；
     但任何从 example 模板新配的机器，"anthropic" 供应商的 upstream 会是
     `http://127.0.0.1:15721`，且没有任何报错；
  4. 同一个文件里 `enabled: ${ZKAI_OLLAMA_ENABLED:-false}` 已经用了 ZKAI_ 前缀
     ——说明加前缀才是本来意图，其余的是漏网。
- **改法**（只动模板与 `.env.example`，现役配置零影响）：
  `config/providers.example.yaml` 里所有网关自己的开关
  （base_url / enabled / referer / app_title）改成 `ZKAI_` 前缀，共 11 个变量名；
  `.env.example` 同步改名并补上全部条目；模板头部加一段说明**为什么**不许用裸名字，
  防止下一个图省事的人改回去。密钥名（`OPENAI_KEY_01` 等）不动——
  它们本来就不和任何工具重名。
- **验证**：三条断言全过——未设变量走官方默认值、劫持裸名字后**仍是**官方默认值、
  设 `ZKAI_` 自己的名字则生效。新增 2 个测试，其中一条是**策略测试**：
  扫描打包的 example 模板，只要出现 tool-owned 名单里的裸名字就红
  （已做变异验证：把模板改回 `${ANTHROPIC_BASE_URL:-`，测试精确失败）。

### 1.11 改完 YAML 不用重启、不用手动 reload——配置文件自动监听（第 4 项，已修）

- **证据（前两轮的「根治项」，一直挂着）**：网关只在启动时读一次配置，内存与磁盘
  长期背离；更甚的是控制台表单用**内存值**渲染，一保存就把运营者的文件编辑覆盖回去
  （2026-09-28/29 一天内吃掉两次改动，见「外部改配置会被静默回滚」那条）。
  上一轮只在 `config_writer` 加了「拒绝覆盖」的闸（把静默错误变成显式 409），
  根因没动：**内存和磁盘依然有可能不一致**。
- **改法**：新增 `app/core/config_watch.py`（`ConfigWatcher`），lifespan 里启动，
  `/health` 暴露 `config_watch`，控制台状态行显示「配置自动生效（已自动 reload N 次）」
  或（关掉时）「配置需手动重载」。四条设计取舍：
  ①**纯标准库 stat 轮询，不引 watchdog/inotify**——为 2 秒一次 stat 加依赖不划算，
     轮询在网络盘/容器里还更可靠；`ZKAI_WATCH_CONFIG` / `ZKAI_WATCH_CONFIG_INTERVAL` 可控；
  ②**按 `(mtime_ns, size)` 判 + settle 窗口**，写了一半的 YAML 不会被加载后报错；
  ③**YAML 写坏不会让网关倒下**：保留上一份配置，`config_watch.last_error` 说清为什么
     没生效，改好后下一次改动自动接上；
  ④**reload 与端点共用 `Container.reload_config()` 一条路径**，否则「点了重载才好用」
     会变成一种可能的状态；reload 后 `watcher.reseed()` 刷新基线，否则同一改动每 2 秒重放。
  监听名单 = `AppConfig.source_files`（真正被 loader 读过的文件），**不是 glob**——
  编辑 `*.example.yaml` 或 `.bak` 不该触发 reload。
  `config/config.example.yaml` 与 `.env.example` 已同步（行为变更两边都改）。
- **验证**：10 个新测试，其中 3 个是**端到端**——在临时配置目录里建真容器、
  改 `models.yaml`，断言 router 的别名**换掉了**（旧别名消失，不是合并）、
  且 `router.plan()` 真的按新配置选模型。另外单独验了：半写文件不加载、
  坏 YAML 保留旧配置且 `last_error` 有内容、开关能关掉。
  全量 **786 passed**（本轮起点 753）。

### 1.12 顺手记下：活网关是 16:56 由你右键重启的，已确认生效

探针就是本轮加的 `config` 段：`GET /health` 现在返回
`{"credential_env_gaps": {"SENSENOVA_API_KEY": ["sensenova-01"]}, ...}`，
进程 PID 34264 启动于 16:56:09，晚于所有代码改动。**右键重启本身没问题**，

改完代码不重启就不会变（这和「配置不 reload 不生效」是同一个病，现在配置那半治好了，
代码那半仍然只能靠重启）。

### 2.1 `ConfigStaleError` 逃出所有写入点的 except——那道 409 是死代码（BLOCKER，已修）

- **证据（已自己复核）**：`ConfigStaleError` 继承 `RuntimeError`，而
  `app/api/admin.py` 的 5 个写入点一律 `except (OSError, ValueError)`。
  `_file_write_failed` 里专门写的 409 + `type=config_stale` + 「先 reload」
  **永不可达**——外部改过配置再从控制台保存，运营者拿到的是 500「网关内部错误」。
  文件仍然被保住了（闸门有效），坏的只是错误形状：把可操作状态伪装成服务器故障。
- **改法**：一处闭合，`class ConfigStaleError(ValueError)`。语义也说得通——
  要写进去的值来自一份**陈旧快照**，这是「值不合法」，不是「文件坏了」（那才是 OSError）。
  没有改那 5 处 except（每处都要记得同步，迟早漏）。
  副作用核对过：`burner_service.write_config` 不走 `atomic_write`，不受影响。
- **验证**：新测试钉在**唯一的消费者**（HTTP 端点）上——旧测试只走到
  `config_writer` 边界，从没走到这里。断言 409 + `type=config_stale` + 文件未被覆盖，
  外加一条 `issubclass(ConfigStaleError, ValueError)` 的类型契约。
  变异验证：把基类改回 `RuntimeError`，测试精确失败。

### 2.2 `exclude_none` 删掉 assistant 工具轮的 `content`——严格上游 400 整条链判死（BLOCKER，已修）

- **证据（已离线复现）**：`build_payload` 用 `message.model_dump(exclude_none=True)`，
  而 Responses 路径的每个工具轮都产生 `ChatMessage(role="assistant", content=None,
  tool_calls=[...])` → 线上 payload 里这条消息**没有 `content` 键**。
  OpenAI 自家 API 容忍，NVIDIA NIM 不容忍：
  `missing field 'content' at line 1 column 3210887`。而 400 被判「调用方的错」
  （不重试/不换 Key/不故障转移）→ 整条请求死在链尾。
  DB 里 2026-09-27 有三个真实请求这么死的（user_agent=claude-cli）。
- **改法**：在协议边界修，不动 canonical 模型——`content is None` 在内部门槛
  （历史裁剪、token 估算）里是有含义的。新增 `_wire_message()`：
  渲染给 OpenAI 兼容格式时，assistant/tool 消息一律带 `content`（空串）。
  空串正是这个字段该有的意思：它没说话，只调了工具。
- **验证**：回归测试逐个断言三条消息都有 `content` 键、且 tool_calls 未丢。
  变异验证：把补齐逻辑改成 `if False`，测试精确失败。
- **没做的那半**（记在 §3）：400 一律当"调用方的错"这件事本身仍可商榷——
  网关自建 payload 被某个上游拒掉时，failover 本来是有效的。但它和"客户端真的
  发错了"共用同一个状态码，放宽会让真错请求白烧 20 次尝试。建议维持现状，靠修根因。

### 2.3 `agent_auto` 降级只查别名"名字"不查"能否解析"（HIGH，已修）

- **证据（已自己复核）**：`known_aliases=set(self.aliases.names())`，而 `names()`
  **包含 `enabled: false` 的条目**；`expand()` 对它们返回空列表 →
  `resolve_model_ids` 抛 `AliasNotFoundError` → 404，且**一句 WARNING 都没有**。
  受影响的是 agent_auto 的全部三类改写目标（带图 / 工具轮 / ≥100k tokens）。
- **改法**：判据从"配置里写过这行"换成"这条路现在走得通"——
  新增 `Router._servable_aliases()`，用与 `resolve_model_ids` **逐字相同**的
  `expand(name, model_ids=set(self.config.models))`：那里返回空就会抛错，
  所以"expand 非空"就是"plan() 走得通"。自己另发明一套标准只会重新造出裂缝。
  警告文案也改成分辨"没配 / 被停用 / 模型全不可达"三种。
- **验证**：3 个新测试（停用别名要降级、target 模型不存在也要降级、降级必须有
  WARNING 不许静默）。变异验证：把 `_servable_aliases` 改回恒真，三条全红。

### 2.6 限流账本只在优雅关闭时落盘，而网关从未优雅关闭过（HIGH，已修）

- **证据（全部自己复核过）**：`app/routing/limits.py:59` 有 `_FLUSH_INTERVAL = 30.0`，
  `flush()` 自带「没脏就不写」和 30s 自限流——但**全仓唯一的调用点是
  `container.shutdown()` 里的 `flush(force=True)`**。而
  `grep -c "ZK-AI stopped" data/gateway.log` → **0**：这个网关从未优雅关闭过。
  于是 `data/rate_limits.json` 的 mtime 停在 **2026-09-25 12:41**，内容只有 3 条
  token 记录（约 3.3k tokens），而此后 DB 里有数千次 sensenova 成功请求。
  `providers.yaml` 里那道「按账号的 token 配额到线就跳过该账号的 Key、
  不再发出注定 429 的请求」的主动闸门，**已经空转 4 天**。
- **为什么比"没这个功能"更糟**：它看起来在工作。状态文件在、计数器在、
  `_FLUSH_INTERVAL` 常量在——只有一条从没人跑过的调用路径。
- **改法**：`Container.start_rate_limit_flush()` 起一个 30s 周期任务调
  `flush()`（无参，不 force），lifespan 启动、shutdown 停止。
  `flush()` 本来就只脏了才写 + 原子替换，所以周期调用大部分时候是空操作。
- **验证**：3 条测试——①无参 `flush()` 也要落盘，重建实例读得回计数；
  ②没脏就不许改写文件（否则一次空转周期会把真状态清成空快照）；
  ③**容器真的起了这个循环**（把间隔压到 50ms 看 flush 被调）。
  第 ③ 条是必要的：只测 ① 的话，lifespan 忘了启动循环也全绿。
  变异验证：把循环体改成直接 return，③ 精确失败。
