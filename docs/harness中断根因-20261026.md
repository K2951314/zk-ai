# harness 与 qoder 中断的根因（2026-10-27 最终版）

> 本文件两次推翻自己。v1 说「AMD 300s 是主因」，v2 说「一个请求打空整池」。
> **两次都错了。** v3 的结论有直接数据支撑，见 §1。数据取自 `data/zkai.db`。

---

## 一句话结论

**主因是 token 吞吐（tpm），不是覆盖不足、不是超时、不是 Key 轮换方式。**

商汤 9 把 Key 从 2026-10-24 04:29 到 15:33 **全程 429**（每把 81~91 次），
不是「被某个请求打空」，是**整池一整天都在限流**。

而每把 Key 每分钟只发 **1.2 个请求**（喂到 rpm 上限 3 之下），
但每个请求平均 **187,139 tokens**（18.7 万），最大 70 万。

**瓶颈是 token 量，不是请求数。**

---

## 一、证据

### 1.1 整池连续限流，中间从未恢复

```
sensenova-07: 91 次 429，04:29:59 → 15:33:29
sensenova-03: 89 次 429，04:30:00 → 15:33:48
sensenova-02: 89 次 429，04:29:49 → 15:33:42
（9 把 Key 全部如此，81~91 次）
```

### 1.2 请求频率远低于 rpm 上限

| Key | 每分钟峰值 | 每分钟均值 |
|---|---|---|
| sensenova-01 | 3 次 | 1.1 次 |
| 其余 8 把 | 2 次 | 1.2 次 |

配置的 rpm 上限是 **3 次/60 秒**。**没有超 rpm。**

### 1.3 但每请求的 token 量极大

成功请求的 input token 分布（10-24 起）：

| 区间 | 次数 |
|---|---|
| <20k | 7 |
| 20-60k | 28 |
| 60-150k | 41 |
| **150-300k** | **145** |
| >=300k | 6 |

平均 187,139 tokens。单分钟池内峰值 **140 万 tokens**（2 次请求）。

### 1.4 429 原文分类

| 类型 | 次数 |
|---|---|
| `tpm/rpm` 混合 | 577 |
| `rpm` | 125 |
| `tpm` | 81 |

混合串是商汤的固定文案（"inference exceeds tpm/rpm limit"），
结合 1.2/1.3，**tpm 是约束项**。

---

## 二、为什么 18.7 万 token/请求

`ds` 客户端是 `deepseek-harness`，它**每轮重发全量历史**。
一场长对话到后来每轮都要重付前面全部内容。

AGENTS.md 已记录同一个杠杆：
> 真正管 token 的是客户端侧：claude-cli 每轮重发全量历史，网关分工管不了它，
> 杠杆是「适时开新会话」。

而历史裁剪开关 `ZKAI_TRIM_HISTORY_TOKENS` **默认 0（关闭）**，
理由是「删上下文可能改变答案，是产品决策，不该藏在默认值里」。

---

## 三、这对「把供应商都试一遍」意味着什么

覆盖不是问题：154 条失败里只有 57 条（37%）只碰过 1 个供应商，
而其余 97 条已经试了 2~3 家——**都失败了**，因为商汤在限流、AMD 在慢/挂。

**试更多次不会让一个 tpm 打爆的渠道变得可用。**

真实的算术：

```
商汤池容量 ≈ 9 把 × (每把 tpm 上限)
需求       ≈ 10 请求/分 × 18.7 万 token = 187 万 token/分
```

要么降低每请求 token（历史裁剪），要么加账号（横向扩容），
要么让客户端开新会话。**没有任何路由改动能解决这个。**

## 四、本次已做的代码改动（仍然有价值，但不是治本）

| 改动 | 治什么 | 实测收益 |
|---|---|---|
| `max_credentials_per_deployment: 9 → 3` | 单个请求不再可能扫满 9 把 | 29% 的请求会被截断到 3 把，把 Key 留给并发请求 |
| `_attempt_timeout`（新增） | 一条慢腿不许吃光整个请求预算 | 3 条腿时首发 95s、2 条时 145s；商汤 227 次成功全在 30s 内，**误杀率 0%** |
| `_wait_for_credential`（新增） | 整池冷却时排队而非瞬时 503 | **实测只能救 0 条**（见下） |

### 一个我必须报告的负面结果

`_wait_for_credential` 的收益我用历史数据验证过：
55 条瞬时 503 之后，下一个商汤成功的中位等待是 **333 秒**。
10 秒的排队上限**一条都救不了**。

它作为兜底仍然合理（避免 0.01 秒的空跑），但**不是解药**，我没有夸大它。

### 一个必须报告的局限

`_attempt_timeout` 对 `ds` 链的**最后一条腿（AMD）没有约束**——
最后一条腿按定义拿走剩余全额预算。要缩短「静默等 AMD」只能降 provider 超时：

| AMD timeout | 保留的成功 | 丢失 |
|---|---|---|
| 300s（现状） | 235 | 0 |
| 120s | 176 | 59 次慢成功 |
| 60s | 134 | 101 次 |

**这是产品决策，我没有替你改。**

## 五、真正的解药（按性价比排序）

| 优先级 | 动作 | 依据 |
|---|---|---|
| **P0** | **开历史裁剪**：`ZKAI_TRIM_HISTORY_TOKENS=60000` | 18.7 万 → 6 万 token，同样 tpm 桶容纳 **3.7 倍**请求 |
| **P0** | **魔搭充值**（`insufficient balance`） | 10-23 它是均 9.3s、189/201 成功的健康腿，回来后 ds 有三腿 |
| P1 | 客户端「适时开新会话」 | harness 侧行为，网关管不了 |
| P1 | 补回 `zk-k3` / `zk-long` / `zk-vision` 三个别名 | 回迁丢失，agent_auto 改写全部回落 |
| P2 | 商汤加账号 | 线性扩容，成本最高 |
| P2 | AMD timeout 300→120 | 见 §4 取舍表 |

## 六、qoder（与上述无关）

1. **额度耗尽**：上游原文 `You have reached the daily usage limit.`，Qoder 自家日限额。
2. **续聊必 404（真 bug，未修）**：委派会话存 `cli:qoder` 当模型，

   复现：`@cli-grinder-qoder` 派任务后，不带 @ 再发一条消息。

## 七、我三次错误更正记录

| 版本 | 错误结论 | 被什么推翻 |
|---|---|---|
| v1 | 「AMD 300s 超时是主因」 | 墙钟型 504 只 15 条，全修也只到 ~80%；且 10-23/24 跑的是 round_robin 不是 priority |
| v2 | 「一个请求打空整池（limit=9 之罪）」 | 172 条瞬时 503 发生在「扫 0 把 Key」的请求之后；真相是整池连续 429 一整天 |
| v3 | 本文 | 直接统计每 Key 每分钟请求数（1.2）与 token 量（18.7 万） |

**教训**：前两次都是「看现象猜机制」，没有量到 token 这个维度就下结论。
真正的判据是「每分钟请求数」（未超 rpm）与「每请求 token 数」（爆 tpm）这两个数。
