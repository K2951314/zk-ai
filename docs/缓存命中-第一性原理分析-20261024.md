# 缓存命中率为什么上不去：第一性原理分析

日期：2026-10-24　｜　触发：粘性修复（799593d）之后命中率仍低（3% → 继续对话 12%）

---

## 0. 先把「不可能」说清楚

「既然都经网关中转，不管哪个供应商都应该趋近 100%」——**这个前提是错的**，
而且错在最关键的地方。KV cache 是**上游 GPU 显存里的一段 prefill 计算结果**，
网关没有、也不可能持有它。网关能决定的只有两件事：

1. 这个请求**落在哪台机器、哪个账号上**（命中率的分母）；
2. 请求字节**是不是上次那段的严格前缀**（命中率的分子）。

「中转」不等于「缓存」。CDN 能加速是因为回源缓存由 CDN 自己管；
这里是**别人的显存**，网关只能「猜」它还在不在、还认不认这段前缀。

### 100% 在数学上就不成立

一场 N 轮的对话，总输入里有 (N-1)/N 是**上一轮的输出**。
第 k 轮整个请求在逻辑上不可能命中——因为它的尾巴是模型刚刚生成的那段，
缓存里还没有。所以**单轮命中率的理论上限天然低于 100%**，
诚实的目标是「命中率 ≈ 前缀占比」而不是「命中率 = 100%」。

### 三种引擎，三种「命中」的定义

| 上游 | 缓存键范围 | 可缓存的最小单位 | 要显式声明吗 |
|---|---|---|---|
| DeepSeek 官方 | 按**账号**，磁盘 KV | **请求边界**与**输出边界**，外加固定间隔切点 | 否，自动 |
| 硅基流动 / 魔搭 / 商汤 | 按**用户 × 模型** | 固定 token 块（如 16）；前缀不足一块则完全不缓存 | 否，自动 |
| Anthropic 原生 | 按 **API key × 模型** | 必须在 `content_control` 打断点（`cache_control`），最多 4 个 | **是** |

第二条最关键：**DeepSeek 的可缓存单位是「整段用户输入」和「整段模型输出」的边界，
不是任意长度前缀。** 这解释了它为什么对「每轮 append」的对话极其友好——
而一旦每轮的前缀有任何一个字节变化，**整条链一次都不命中**（不是命中率下降，是归零）。

## 1. 三条与路由无关的「归零」路径

粘性只解决「打到同一个部署」。但下面三条里，**任何一条命中，粘性都白费**。

### 1.1 凭据（账号）在部署内部继续轮换 —— 最可能的元凶

`scheduler.py` 有两级轮换：

```
for deployment in plan.candidates:          # 部署级（粘性管这一级）
    for credential in pool.candidates():    # 凭据级 ← 粘性没管
```

`_apply_deployment_affinity()` 只把 deployment 提到最前，
但同一个 deployment 下面**有 9 把商汤 Key**，凭据池按 `weighted` 每请求重抽。
商汤的缓存键是「用户 × 模型」，**换 Key 就是换用户 → 换缓存空间 → 新空间是空的**。

`pool._apply_affinity` 本来就有凭据级亲和（`note_affinity`），但它有两个漏洞：

- **成功率不是 100%**：`weighted` 策略下，8/9 的概率没被 float 上去 → 换账号 → 冷缓存；
- **失败一轮就换锚**：`note_affinity` 只在成功时重锚，而**下一轮只要换了一次 Key，
  新锚就又绑到别人身上**。于是「轮换 → 冷却 → 再换 → 再冷」会自我维持一段时间。

实测的 3%→12% 这个量级，跟「大部分轮次换了账号」完全吻合。

### 1.2 `sampling 参数 → 上游模板 → 渲染出的 prompt 变了`

网关把 OpenAI 语义翻成各家的 chat template。**模板一换，上游看到的字符串就变**，
前缀匹配立刻断。常见的翻转源：

- `reasoning_effort: max`（deepseek-flash 部署上配的就是 max）——开启思考可能改变
  模板拼装方式或以不同方式插入特殊 token；
- 客户端某些轮带 `temperature`、某些轮不带 → 网关省略键 → 上游取缺省，模板分支可能不同；
- `tool_choice` 在「有 tools」和「无 tools」之间抖动 → `payload.pop("tool_choice")` 分支。

**这一条需要实测确认，不是猜的结论**（见 §3 的诊断步骤）。

### 1.3 历史裁剪一旦触发，前缀永久作废

`trim_history` 默认关闭（`trim_history_tokens: 0`），但一旦有人打开，
它会在系统消息后插入一行「已省略更早的 N 条历史」——**这一行每轮的数字都在变**
（N 随裁剪量变化）。等于**每一轮都把前缀改了一次**，缓存彻底归零。

同类：`app/services/agent/service.py:777` 的上下文压缩（head/summary/tail 重建），
每压缩一次就是一次前缀重写。

## 2. 粘性实现本身的三个缺口

即便是「打到同一个部署」这件事，现在的实现也有 3 处漏掉：

### 2.1 粘性键的种子取了 `messages[0]`

```python
seed = f"{request.model}\x00{opener[:4000]}"   # opener = messages[0]
```

- `/v1/chat/completions` 的 `messages[0]` 是 **system prompt**（稳定，OK）；
- `/v1/messages`（Anthropic 入站）的 `messages[0]` 是 **用户第一条消息**
  （见 `anthropic.py:100`：system 被单独放到前面，然后才是 user）。

**两种协议对同一个物理内容得出了两个不同的哈希**，于是 `h:xxx` 与 `h:yyy`
各钉各的。如果客户端中途换协议（Claude Code 走 `/v1/messages`、Codex 走 `/v1/responses`），
同一条对话会被当成两条会话。

更严重的是，若客户端不传 `session_id`（Claude Code 会发 `metadata.user_id`，
但网关**忽略 metadata**，见 `messages.py:22`），哈希种子落在用户消息上——
而 `/v1/responses` 路径的 `messages[0]` 是 `instructions`（system），
**协议之间根本不收敛**。

### 2.2 容量写成 64

```python
self._deployment_affinity_max = max(16, int(getattr(pool, "affinity_max_sessions", 64) or 64))
```

`pool.affinity_max_sessions` 的配置默认是 **4096**（`config.yaml` 的
`credential_affinity.max_sessions`，见 `container.py:419`），但这里用
`getattr(pool, "affinity_max_sessions", 64)` —— **属性名根本不存在**
（池里叫 `_affinity_max_sessions`，带下划线，`pool.py:74`），所以永远回落到 64。
**改配置救不了它**：运营者把 `max_sessions` 调到多大，粘性容量都是 64。

对照：紧挨着的 TTL 那行 `getattr(pool, "affinity_ttl", 1800.0)` 是**通的**
（`pool.py:73` 的属性名恰好没带下划线）。两行写法一样的 getattr 一好一坏，
正说明「猜属性名」这种写法本身就该消失。

> **已修（2026-10-24 当天，含对抗式审查补刀）**：pool 暴露公开属性
> `affinity_max_sessions`，scheduler 写粘性条目时**现场读池子**（连构造期
> 快照也不要——审查发现快照会在热重载后变陈旧）；reload 补读
> `credential_affinity` 段（`pool.apply_affinity_config`），配置存盘即生效。
> 回归测试 `test_deployment_affinity_capacity_follows_the_pool`（行为测，
> 变异法验证过鉴别力）与 `test_editing_the_affinity_section_reaches_the_pool` 钉住。

64 条会话的 LRU，在多开的 agent 场景下一小时就滚完了。**滚出去 = 重新冷启动。**

### 2.3 粘性只锚成功，不锚「冷启动成本」

现在只要成功一次就记一笔。但更该记的是：**这次请求打了多少 token**。
一个 5 万 token 的前缀，粘错了要重付 5 万；一个新开的两轮小对话，粘错了几乎无所谓。
按 token 量加权，能把有限的粘性容量用在真正贵的地方。

## 3. 怎么验证到底是哪一条（先测，别改）

新增一个**只读诊断端点**，把每个请求的「命中/未命中」理由摆出来——现在是瞎猜，
因为网关根本不记录缓存命中（`usage_records.cached_tokens` 已经加了列，
但**索引里没有任何地方把它写进日志**，`gateway.log` 里 `grep cached` 为 0）。

最小可验证的三步：

1. **同一个客户端、连续 5 轮、固定 `session_id`**，抓 `x-zkai-provider` +
   `x-zkai-credential` 响应头 —— 看凭据是否在轮次之间跳；
2. 同一组请求，把 `providers.yaml` 里该供应商的凭据**临时缩到 1 把**，
   重跑 —— 如果命中率跳到 80%+，§1.1 实锤；
3. 再固定 `temperature`/`reasoning_effort`（客户端显式传），重跑 —— 看 §1.2。

**这三步不用改一行代码就能做，成本半小时。** 在此之前不要动粘性逻辑。

## 4. 按投入产出排序的改法

### A. 凭据级粘性必须是**硬的**（最高优先级）

现在的 `_apply_affinity` 是「floats the pinned credential to the front」，
注释自己写了 *it must still be usable*。但真正想要的语义是：

> 只要这把 Key **可用**（没冷却、没超配额、没被禁用），**就用它**，不要按 weight 重抽。

改动很小：`_apply_affinity` 命中时把 pinned credential 放到 index 0 并**只返回它**，
后面的作为故障转移后备。代价是负载不均——但**缓存命中省下的钱远大于负载不均的代价**，
而且 9 把 Key 的配额本来就是按账号独立算的。

### B. 粘性键收敛到「协议无关的会话身份」

优先级：`session_id` > `metadata.user_id`（现在被忽略）> **`messages[0]` 取第一个 system 角色**
> 首个 user 消息指纹。让 `/v1/messages` 与 `/v1/chat/completions` 对同一场对话算出同一个键。

顺带把 `extra["prompt_cache_key"]`（Responses 路径目前 accepted-and-ignored，
见 `request.py:302`）也纳入种子——OpenAI 客户端会主动发这个字段，它是**最诚实的会话标识**。

### C. 容量别用魔数，读配置

`getattr(pool, "affinity_max_sessions", 64)` → 用池里**真实的属性名**
`_affinity_max_sessions`（`pool.py:74`），或给 pool 加一个公开属性——
scheduler 构造时只拿得到 pool，读不到 config。配置键是
`credential_affinity.max_sessions`（默认 4096）；**在这次修复落地之前，
改这个配置完全不生效**，这点要向运营者说清。

### D. TTL 按「上游缓存的实际存活时间」设，而不是复用凭据的 1800s

DeepSeek 官方文档：缓存「在使用中断后通常几小时到几天内自动清除」。
所以 30 分钟的 TTL **偏短**——吃完午饭回来，粘性已经过期，第一次请求必然冷启动。
给粘性单独一个 TTL（比如 4 小时），比凭据亲和长得多才对，因为它的失效代价更高。
（核实过：TTL 的 getattr 是通的，今天就能用 `credential_affinity.ttl_seconds`
调——但那是凭据亲和的键，调它会把凭据粘性一起拉长，所以「单独一个键」仍然是对的。
对抗式审查补刀：热重载原本**不重读**这一段，改 TTL 得重启进程；已接进
`reload_config`，现在存盘即生效。）

### E. 记录命中，才有优化空间

`usage.cached_tokens` 已经全链打通（`response.py` 的 `_lift_openai_cached_tokens`），
但**没有落进日志，也没有进 `/health`**。至少：

- 每条请求日志尾加 `cached=12345/50000 (24%)`；
- 控制台 KPI 加一行「缓存命中率」——**没有这个数字，所有优化都是猜测**。

> **已落地（2026-10-24 当天，第一项）**：`Scheduler._log_usage` 在非流式/流式
> 两条成功路径打 `usage <provider>/<model> key=<id>: prompt=N cached=N (P%) completion=N`；
> 粘性侧同步加了换锚日志（`session … re-anchored: A -> B`）与粘性被跳过的
> 原因日志（`pin skipped … status=cooldown[, rate window full]`）。
> 控制台 KPI 尚未做。

### F. 上游不认前缀时，网关没有可做的事（诚实地说）

如果 §1.2 实测确认是「模板/参数导致的渲染漂移」，**网关侧无解**——
那是上游的行为。唯一的缓解是：**把同一场对话锁在同一个部署上，并且参数冻结**
（网关替客户端补齐缺省值，让每轮 payload 的键集合完全一致）。

## 5. 结论

1. **100% 不可能**，理论上限是「前缀占比」，N 轮对话约 (N-1)/N；
2. 粘性修复只解决了「部署级」这一层，**凭据级还在轮换**——这是最可能的元凶，
   因为换 Key 就是换账号就是换缓存空间；
3. 粘性实现有 3 个具体的 bug/缺口（协议不收敛的键、64 的容量魔数、30 分钟的短 TTL）；
4. **先测再改**：缩到 1 把 Key 重跑 5 轮，半小时就能实锤；
5. 网关不是 CDN。它能做的只有「钉住」和「不改字节」，两件事都做到位，
   命中率才会趋近理论上限。
