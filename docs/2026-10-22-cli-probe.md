摸清它们的非交互调用方式、认证形态与错误分类，为阶段 1 适配层设计提供事实依据。

## 探测结果

### 已安装工具

| 工具 | 命令 | 版本 | 来源 |
|---|---|---|---|
| Qwen Code | `qwen` | 0.24.6 | npm 全局 @qwen-code/qwen-code |

注意：可执行命令名是 `qwen`（/usr/bin/qwen -> cli-entry.js），不是 `qwen-code`。

### 未安装工具

claude、codex、qoder、workbuddy、catpawai、aider、cursor、gemini、copilot
均不在 PATH；npm 全局包中也不存在。

### qwen 非交互能力（来自 --help 与实测）

- 一次性模式：位置参数直接给 prompt（`qwen "任务"`），`-p/--prompt` 已弃用但仍可用
- 模型选择：`-m/--model`
- 审批模式：`--approval-mode` 支持 plan（只分析，不改文件不执行命令，最安全）/
  default / auto-edit / auto / yolo
- 输出格式：`-o/--output-format` 支持 text / json / stream-json
- 认证方式：`--auth-type` 支持 openai / openai-responses / anthropic / qwen-oauth /
  gemini / vertex-ai
- OpenAI 兼容参数：`--openai-base-url`（自定义后端）+ `--openai-api-key`
- 超时/限额相关：未见显式全局超时参数，需外层包住（适配层用 asyncio.wait_for 实现）

### 错误形态实测

1. 未配置认证时（~/.qwen 不存在、无环境变量）：
   输出『No auth type is selected. Please configure an auth type ... before running
   in non-interactive mode.』——属『未登录』类，特征明确，已收录进适配层
   base.py 的 _AUTH_PATTERNS

### 待验证（被暂停，待继续）

1. qwen 指向本机网关的端到端调用：
   `qwen --auth-type openai --openai-base-url http://127.0.0.1:8318/v1
   --openai-api-key <任意非空> -m zk-auto --approval-mode plan "最小任务"`
   ——网关 /v1/models 无鉴权，但 chat 接口是否要求特定 key 待实测
2. qwen 通过网关跑通后：验证 json 输出格式、超时行为、额度耗尽（429）报错形态
3. 若 qwen 官方免费额度（qwen-oauth）可用：对比『走官方免费池』与『走 zkai 网关』
   两种模式的成本与稳定性，决定 delegate_cli 中 qwen 的默认接入方式

## 结论（阶段性）

- 本机现阶段唯一可调度的外部 CLI 是 qwen；claude/codex 等需要后续安装
- qwen 原生支持 OpenAI 兼容后端，与 zkai 网关天然契合，
  阶段 1 适配层已把它作为第一个接入对象（QwenAdapter 已写好）
- 『未登录』错误分类的第一条特征已入库；『额度耗尽』『执行失败』两类待实测补齐
